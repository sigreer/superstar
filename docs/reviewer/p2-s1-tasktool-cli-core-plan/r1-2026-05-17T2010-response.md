1. Findings

F1. Severity: blocking — Test commands will not import the package as written.
`docs/plans/2026-05-17-p2-s1-tasktool-cli-core.md:51`, `131`, `219`, and repeated task gates run `python3 -m unittest ...` from repo root, but the package lives under `tools/tasktool/` and tests import `tasktool` directly. Without `PYTHONPATH=tools` or a `-t tools` discovery root, most test modules will fail before exercising the code.

F2. Severity: blocking — The plan’s own stated end-to-end command cannot work.
The goal says `tasktool init && tasktool create phase --title "..." && tasktool show P1` should round-trip (`docs/plans/...:5`), and the spec makes `--project` optional (`docs/specs/2026-05-17-P2-tasktool-design.md:183`). The planned argparse requires `init --project` (`docs/plans/...:2383-2385`), so the acceptance path fails.

F3. Severity: important — ID resolution does not meet the spec’s “short when unambiguous” contract.
The spec says CLI `<id>` arguments accept fully-qualified IDs or short forms when unambiguous (`docs/specs/...:162-164`, `176-178`). The planned `_find_item` rejects any short slice/task (`docs/plans/...:1674-1677`), and `cmd_create_task` requires a fully-qualified slice ID (`docs/plans/...:1493-1495`). Add resolution logic and tests for unambiguous `S1`/`T1`, plus rejection when ambiguous.

F4. Severity: important — Validation omits spec-required checks.
The spec requires ISO date format and path existence warnings for `spec_path`, `plan_path`, and `refs[]` (`docs/specs/...:166-174`). The planned validator only compares date strings lexically (`docs/plans/...:847-849`) and does not inspect path fields at all (`docs/plans/...:894-905`). Add concrete warning/error representation and tests for malformed dates and missing paths.

F5. Severity: important — Global CLI flags from the spec are missing.
The spec defines `--quiet`, `--verbose`, and `--no-stage` (`docs/specs/...:270-275`). The planned parser only has `--project-root` (`docs/plans/...:2377-2381`), and Task 14 stages on every save with no opt-out (`docs/plans/...:2612-2616`). At minimum, implement `--no-stage` or explicitly defer it.

F6. Severity: minor — The “all tests” command in Task 13 is likely a false gate.
`python3 -m unittest tools.tasktool.tests -v` (`docs/plans/...:2541`) can import only the package module and run zero tests, depending on discovery behavior. Use the same explicit discovery command, with corrected import path, for every full-suite gate.

2. Open questions / assumptions

- Is `tasktool init --project` intended to be required despite the spec showing it optional?
- Are path existence checks meant to be warnings only in CLI output, while `validate_project()` remains error-only?
- Should S1 intentionally defer `--quiet`, `--verbose`, and `--no-stage`, or are they required for first usable CLI parity?

3. Suggested document edits

- Change all test commands to something like: `PYTHONPATH=tools python3 -m unittest discover -s tools/tasktool/tests -v`.
- Make `init --project` optional with a default derived from `repo_root.name`, or revise the goal/spec to require it.
- Add a resolver task for unambiguous short IDs.
- Extend validation task with date-format and path-warning tests.
- Add global flag parsing and plumb `--no-stage` into `_save`.

4. Verification gaps / commands

- `PYTHONPATH=tools python3 -m unittest discover -s tools/tasktool/tests -v`
- CLI smoke: `PYTHONPATH=tools python3 -m tasktool init --project demo` and, if kept as acceptance, also `PYTHONPATH=tools python3 -m tasktool init`
- Add negative tests for ambiguous short IDs and malformed dates.
