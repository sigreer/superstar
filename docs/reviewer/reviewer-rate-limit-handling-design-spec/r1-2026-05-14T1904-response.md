1. Findings

F1. Severity: blocking. The codex regex in [docs/specs/2026-05-14-reviewer-rate-limit-handling-design.md](/home/simon/Dev/sigreer/skills/superstar/docs/specs/2026-05-14-reviewer-rate-limit-handling-design.md:94) escapes the alternation pipe: `(?:AM\|PM)?`. That matches literal `AM|PM`, not `AM` or `PM`, so the sample stderr at line 13, `try again at 6:48 PM`, will not satisfy the acceptance gate at line 282. Use `(?:AM|PM)?`.

F2. Severity: blocking. The spec introduces `status="rate-limited"` in chain entries at [line 123](/home/simon/Dev/sigreer/skills/superstar/docs/specs/2026-05-14-reviewer-rate-limit-handling-design.md:123), but it does not specify updates to existing status-sensitive logic. Current resolution gating only bypasses `status == "failed"` in [external-reviewer.py](/home/simon/Dev/sigreer/skills/superstar/skills/external-review/scripts/external-reviewer.py:1179), so a post-slice/post-phase rate-limited round with `verdict_valid=false` would require an impossible `rN-resolution.md` on the next invocation. The preamble skip text also only documents failed/unknown behavior in [external-reviewer.py](/home/simon/Dev/sigreer/skills/superstar/skills/external-review/scripts/external-reviewer.py:447). The spec needs to define whether `rate-limited` is treated like a process failure everywhere, or avoided as a persisted round when the user chooses hold/schedule.

F3. Severity: important. The schedule path depends on a `schedule` skill at [lines 237 and 244](/home/simon/Dev/sigreer/skills/superstar/docs/specs/2026-05-14-reviewer-rate-limit-handling-design.md:237), but this repo has no schedule/routine skill files (`rg --files skills | rg 'schedule|routine'` returned no matches). This is currently an ungrounded dependency. Either add the schedule skill as part of scope, name an existing concrete mechanism, or move scheduled retry to a non-goal for v1.

F4. Severity: important. The global state path in [line 52](/home/simon/Dev/sigreer/skills/superstar/docs/specs/2026-05-14-reviewer-rate-limit-handling-design.md:52) has no test override. The test plan at [lines 261-267](/home/simon/Dev/sigreer/skills/superstar/docs/specs/2026-05-14-reviewer-rate-limit-handling-design.md:261) would otherwise read/write the developer’s real `~/.config/superstar/reviewer-state.json`. Specify an env var or CLI override such as `AGENT_REVIEWER_STATE_FILE` for tests and controlled runs.

F5. Severity: minor. The architecture says “Three new subcommands” while listing four: `manual-approve`, `ingest-response`, `show-limit`, `clear-limit` at [line 43](/home/simon/Dev/sigreer/skills/superstar/docs/specs/2026-05-14-reviewer-rate-limit-handling-design.md:43).

2. Open questions / assumptions

I assume `rate-limited` is intended to preserve audit history, but the spec should clarify whether every pre-spawn refusal appends a new round. As written, repeated “hold” choices could create multiple chain rounds without reviewer work.

3. Suggested document edits

Fix the regex, add an explicit “rate-limited status semantics” subsection covering resolution gate, incremental preamble, merged verdict, JSON `verdict_valid`, and next-round behavior. Add a state-file override for tests. Replace the schedule dependency with an existing concrete skill/mechanism or remove it from v1 scope.
