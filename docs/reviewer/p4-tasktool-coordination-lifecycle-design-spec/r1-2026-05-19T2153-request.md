### docs/specs/2026-05-19-p4-tasktool-coordination-lifecycle-design.md

    1	# P4 — Tasktool Coordination and Lifecycle Authority
    2	
    3	**Status:** proposed
    4	**Date:** 2026-05-19
    5	**TASKLIST entry:** `P4` in `docs/tasklist.json`
    6	
    7	## Objective
    8	
    9	Make `tasktool` the enforced authority for two workflow rules that are currently left to agent discipline:
   10	
   11	1. Parallel implementation worktrees must not own `docs/tasklist.json` mutations.
   12	2. Active slices and tasks must pass through `in_progress` instead of jumping from `ready` to `done`.
   13	
   14	The intended outcome is that agents can keep using normal `tasktool` commands from whatever checkout they are working in, but the tool decides where writes land and which lifecycle transitions are valid.
   15	
   16	## Problem
   17	
   18	`docs/tasklist.json` is the single source of truth, but linked implementation worktrees currently mutate their local copy. When those branches merge back to `main`, tasklist updates from multiple agents collide as byte-level JSON diffs. This is predictable because each worktree was forked from a stale snapshot of the tracker.
   19	
   20	The same workflow has a status-quality issue: agents rarely mark slices or tasks `in_progress`. Rows remain `ready` until they are closed, which makes `tasktool list --open`, `phase-status`, and human progress scans much less useful.
   21	
   22	These are not independent usability nits. They expose the same architectural gap: `tasktool` has the canonical data model, but it does not yet enforce the coordinator lifecycle strongly enough.
   23	
   24	## Design Summary
   25	
   26	`tasktool` gains two linked capabilities:
   27	
   28	- **Authoritative checkout routing.** Mutating commands invoked from implementation worktrees are applied to a configured authoritative checkout, normally the project `main` checkout, under a lock. Worker worktrees treat `docs/tasklist.json` as a read-only mirror.
   29	- **Lifecycle start enforcement.** `tasktool start <id>` becomes the normal way to begin work. Slice close is allowed only after a slice has been observed `in_progress`, unless an explicit bypass is supplied and recorded.
   30	
   31	The skills are updated to describe the new command surface, but correctness does not depend on prose. The CLI enforces the rules.
   32	
   33	## Configuration
   34	
   35	Add a project-local config file:
   36	
   37	```json
   38	{
   39	  "schema_version": 1,
   40	  "tasklist": {
   41	    "mutation_mode": "authoritative-checkout",
   42	    "authoritative_branch": "main",
   43	    "authoritative_root": "/home/simon/Dev/sigreer/multistore"
   44	  }
   45	}
   46	```
   47	
   48	The default path is `.tasktool/config.json`. `tasktool config init-authority` writes the file for the current checkout. If no config exists, current behavior remains unchanged so existing projects do not break abruptly.
   49	
   50	Field semantics:
   51	
   52	- `mutation_mode`
   53	  - `local`: existing behavior; mutate the current checkout.
   54	  - `authoritative-checkout`: route mutating commands from linked worktrees to `authoritative_root`.
   55	- `authoritative_branch`: branch the authoritative checkout must be on when accepting writes.
   56	- `authoritative_root`: absolute path to the checkout that owns `docs/tasklist.json` writes.
   57	
   58	## Mutating Commands
   59	
   60	The routing layer applies to all commands that write `docs/tasklist.json`:
   61	
   62	- `init`
   63	- `create phase|slice|task|cross`
   64	- `set`
   65	- `start`
   66	- `close`
   67	- `block`
   68	- `unblock`
   69	- `deps`
   70	- `ratify`
   71	- `planning-path`
   72	- `note`
   73	- `ref`
   74	- `title`
   75	- `archive-phase`
   76	- `import`
   77	- `validate --normalise`
   78	
   79	Read commands keep using the current checkout by default, but they should warn when authoritative routing is configured and the current worktree copy is older than the authoritative copy. A follow-up may add `--source authoritative|local`; P4 does not need it.
   80	
   81	## Routing Rules
   82	
   83	For every mutating command:
   84	
   85	1. Discover the current repository root and git common directory.
   86	2. Load `.tasktool/config.json` if present.
   87	3. If `mutation_mode` is absent or `local`, mutate the current checkout.
   88	4. If already in `authoritative_root`, mutate normally.
   89	5. If in a linked worktree, acquire an exclusive lock under the common git directory.
   90	6. Validate that `authoritative_root` exists, is a git checkout for the same repository, is on `authoritative_branch`, and has no unresolved merge.
   91	7. Validate that `authoritative_root/docs/tasklist.json` is not dirty in a way that cannot be attributed to tasktool's own current command.
   92	8. Load and mutate `authoritative_root/docs/tasklist.json`.
   93	9. Save canonical JSON and best-effort stage the authoritative path.
   94	10. Print a concise message naming the authoritative checkout used.
   95	
   96	The implementation should centralize this routing in one module so command functions do not each grow git-worktree logic.
   97	
   98	## Reviewer Chains From Worktrees
   99	
  100	`tasktool close <slice-id>` and `tasktool set <id> --status done` must preserve review-gate semantics when invoked from an implementation worktree.
  101	
  102	The gate should evaluate reviewer artifacts relative to the invocation checkout because that is where post-slice review was run. The resulting `reviewer_chain` recorded into the authoritative tasklist remains a repo-relative path, for example:
  103	
  104	```text
  105	docs/reviewer/p11-s4c-nav-footer-P11-S4c-post-slice
  106	```
  107	
  108	If the reviewer chain path is outside the repository, the command refuses it. If the same repo-relative reviewer chain does not exist in the authoritative checkout yet, close still records the relative path; merge-back will bring the artifacts over. The JSON record must not depend on absolute worktree paths.
  109	
  110	## Lifecycle Enforcement
  111	
  112	Add:
  113	
  114	```sh
  115	tasktool start <id>
  116	```
  117	
  118	Behavior:
  119	
  120	- Accepts phases, slices, tasks, and cross-cutting items.
  121	- Resolves short IDs exactly like `set`.
  122	- Refuses `done` items.
  123	- Refuses `blocked` slices unless `--resume` is supplied, in which case it clears `blocked_on` and sets `in_progress`.
  124	- Sets `status: in_progress`.
  125	- Records a machine-readable lifecycle marker that proves the item was started before close.
  126	
  127	The marker should be explicit rather than inferred from current status, because a row may later move from `in_progress` to `blocked` and back. Add `started: YYYY-MM-DD | null` to phase, slice, task, and cross-cutting records. Existing files load with `started: null`.
  128	
  129	Close behavior:
  130	
  131	- Closing tasks and cross-cutting items from `ready` remains allowed for now, because they are often small bookkeeping rows.
  132	- Closing slices from `ready` is refused unless `--allow-ready-close` is supplied.
  133	- `--allow-ready-close` appends an audit note with timestamp and reason.
  134	- Closing phases from `ready` remains allowed only through `archive-phase`; phase lifecycle is already gated by completed slices.
  135	
  136	This targets the recurring operational pain without making every tiny task transition noisy.
  137	
  138	## Skill Updates
  139	
  140	Update these skills:
  141	
  142	- `tasklist-discipline`: explain authoritative routing, `tasktool start`, and the `ready -> done` slice close guard.
  143	- `using-git-worktrees`: say worktrees may invoke tasktool mutations, but mutations route to the authoritative checkout when configured.
  144	- `subagent-driven-development`: after selecting a ready slice and before dispatching implementation subagents, run `tasktool start <slice-id>`.
  145	- `executing-plans`: replace the current prose-only "Mark as in_progress" step with `tasktool start <slice-id>`.
  146	- `writing-plans`: plans for slice execution should include `tasktool start <slice-id>` as the first execution step when `docs/tasklist.json` exists.
  147	
  148	The status problem is partly skill markdown today, especially in `subagent-driven-development`, but the P4 fix should not rely on skill wording alone.
  149	
  150	## Slices
  151	
  152	### P4.S1 — Authoritative Tasklist Mutations
  153	
  154	Add config loading, git worktree detection, lock acquisition, routing helpers, and command integration for all tasklist-writing commands. Worker worktrees stop committing `docs/tasklist.json` deltas.
  155	
  156	### P4.S2 — Lifecycle Status Enforcement
  157	
  158	Add `started` fields, `tasktool start`, close-time enforcement for slices, and skill updates that make lifecycle transitions visible and routine.
  159	
  160	Depends on: `P4.S1`, because lifecycle commands should use the same routed-write path.
  161	
  162	## Acceptance Criteria
  163	
  164	- `tasktool validate --strict-format` passes on existing tasklist files.
  165	- Tasktool unit and CLI tests cover local mode, authoritative mode, linked worktree routing, lock contention, unsafe authoritative checkout states, and reviewer-chain recording from a worker worktree.
  166	- A simulated worker worktree can run `tasktool close P1.S1 --reviewer-chain ...` and leave the worker copy of `docs/tasklist.json` unchanged while updating the authoritative checkout.
  167	- `tasktool start P1.S1` sets `status: in_progress` and `started`.
  168	- `tasktool close P1.S1` refuses a never-started slice unless `--allow-ready-close --reason "..."` is supplied.
  169	- Skills describe the enforced workflow without asking agents to hand-edit tasklist state.
  170	
  171	## Non-Goals
  172	
  173	- Do not build a semantic `tasktool merge` command in this phase. It is a fallback for a worse invariant.
  174	- Do not move task state outside the repository.
  175	- Do not add networked locking or a daemon.
  176	- Do not require all existing projects to adopt authoritative routing immediately.
  177	- Do not force every task row through `in_progress` before close in this phase.
