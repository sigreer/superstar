**Findings**

F1 — Severity: blocking — The locking rule does not protect the authoritative checkout itself.  
[docs/specs/2026-05-19-p4-tasktool-coordination-lifecycle-design.md](/home/simon/Dev/sigreer/skills/superstar/docs/specs/2026-05-19-p4-tasktool-coordination-lifecycle-design.md:28) says authoritative mutations happen “under a lock,” but the routing algorithm exits early when already in `authoritative_root` at line 88, before lock acquisition at line 89. That leaves a race between a worker-routed write and a direct main-checkout `tasktool` write, which is exactly the collision class P4 is meant to remove. Make the lock mandatory for every authoritative-mode mutation, including invocations from `authoritative_root`.

F2 — Severity: important — Config propagation is under-specified for linked worktrees and machine-local paths.  
The spec adds `.tasktool/config.json` with an absolute `authoritative_root` at lines 35-48, but does not say whether this file is committed, ignored, copied into linked worktrees, regenerated per worktree, or overridden by env/CLI. If it is committed, the absolute path is user-machine specific; if it is untracked, worker worktrees may not have it and silently fall back to local mutation per line 48. This needs a concrete policy before implementation.

F3 — Severity: important — Reviewer-gate routing needs a sharper contract for two-root commands.  
Lines 100-108 correctly identify that close/set must evaluate reviewer artifacts relative to the invocation checkout while writing JSON in the authoritative checkout. The current implementation couples gate discovery and recorded relative paths to a single `repo_root` in [tools/tasktool/commands.py](/home/simon/Dev/sigreer/skills/superstar/tools/tasktool/commands.py:216) and [tools/tasktool/reviewer_gate.py](/home/simon/Dev/sigreer/skills/superstar/tools/tasktool/reviewer_gate.py:25). The spec should explicitly require separate `invocation_root` and `write_root` plumbing, and acceptance should cover both `close` and `set --status done`, relative explicit chains, absolute path rejection, and chains absent from the authoritative checkout.

F4 — Severity: important — `started` enforcement conflicts with the existing `set --status in_progress` path.  
The spec adds `tasktool start` and uses `started` as the proof of prior progress at lines 112-133, but `set --status in_progress` already exists and is part of the current CLI at [tools/tasktool/cli.py](/home/simon/Dev/sigreer/skills/superstar/tools/tasktool/cli.py:56). The spec does not say whether `set --status in_progress` becomes an alias for `start`, is rejected for startable items, or sets `started`. Without that, an agent can still perform the old transition and later be refused at close despite having visibly moved the row through `in_progress`.

**Open Questions / Assumptions**

- Should `.tasktool/config.json` be committed, gitignored, or generated per checkout?
- Should authoritative-mode writes from `authoritative_root` also print the routing message, or only worker-routed writes?
- Should read commands warn based on mtime, git blob SHA, tasklist checksum, or some explicit authority metadata?
- Is `started` intended to be required in canonical JSON after migration, or omitted/null-compatible for older files?

**Suggested Document Edits**

- In Routing Rules, move lock acquisition before the “already in authoritative_root” branch, or state that all authoritative-mode mutations use the same lock.
- Add a “Config lifecycle” subsection covering tracked/untracked behavior, worktree discovery, path portability, and failure mode when authoritative config is missing in a worker.
- Add a “Two-root command contract” subsection: invocation root for reviewer artifacts and user arguments; write root for tasklist load/save/stage.
- Define `set --status in_progress` behavior relative to `start`.
- Expand acceptance criteria for `set --status done`, explicit reviewer-chain paths, stale/missing worker config, and direct authoritative-checkout lock contention.
