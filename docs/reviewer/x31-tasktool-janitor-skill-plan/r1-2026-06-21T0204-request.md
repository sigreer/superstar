    7	## Problem
    8	
    9	Superstar-managed repos accumulate open cross-cutting rows as phases finish, plans change, and follow-up work gets superseded. Cleaning those rows is deceptively risky: a stale title can look obsolete even when source, docs, or reviewer chains prove the work is still live; a row can be old without being abandoned; and a single coordinator reviewing twenty unrelated rows in one context is likely to flatten evidence into guesses.
   10	
   11	The repo already has `tasklist-discipline` for tasktool lifecycle rules and `dispatching-parallel-agents` for independent investigations. What is missing is a reusable on-demand cleanup skill that teaches agents how to run tracker janitorial work: start read-only, split row audits into bounded worker assignments, require a per-row evidence dossier, reconcile recommendations conservatively, ask the user before mutation, and only then apply approved `tasktool` commands in small validated batches.
   12	
   13	The motivating validation repo is `/home/simon/Dev/sigreer/multistore`, where many open `X*` cross-cutting rows need careful cleanup. The new skill must remain generic across Superstar/tasktool repos and must not hard-code multistore phases, paths, or row IDs.
   14	
   15	## Goals
   16	
   17	- Add a new on-demand Superstar skill named `tasktool-janitor`.
   18	- Trigger for prompts such as "clean up the tasktool crosscuts using janitor skill", "audit stale X rows", or "review open cross-cutting/phase/slice cleanup candidates".
   19	- Specialize tracker cleanup methodology without duplicating all of `tasklist-discipline`.
   20	- Make evidence dossiers the mandatory output unit for each reviewed row.
   21	- Coordinate worker agents for heterogeneous or large row sets instead of letting one context bulk-review everything.
   22	- Prevent mutation until the coordinator has presented grouped recommendations and received user approval.
   23	- Preserve a durable audit trail for substantial cleanup unless the user explicitly requests chat-only output.
   24	
   25	## Non-Goals

   28	- No automatic bulk close/cancel behavior.
   29	- No project-specific multistore logic.
   30	- No replacement for `tasklist-discipline`; the janitor skill composes with it for lifecycle semantics.
   31	- No implementation work in target repos while auditing cleanup candidates. If a row needs real code or docs work, the recommendation is `promote` or `keep`, not an inline fix.

   41	The frontmatter should use trigger-only wording:
   42	
   43	```yaml
   44	---
   45	name: tasktool-janitor
   46	description: Use when cleaning up open tasktool rows, especially cross-cutting X items, stale phase/slice entries, or large sets of heterogeneous tasklist cleanup candidates
   47	---
   48	```
   49	
   50	## Required Workflow
   51	
   52	### 1. Read-Only Intake
   53	
   54	The skill must start by loading `superstar:tasklist-discipline` and then running:
   55	
   56	```bash
   57	tasktool list --open
   58	git status --short
   59	```
   60	
   61	When the user asks for crosscuts, the coordinator isolates `X*` rows from the open list before dispatch. The skill may inspect `tasktool show <id>`, specs, plans, handoffs, reviewer chains, archived task notes, source files, docs, recent commits, and targeted `rg` results, but it must remain read-only during classification.
   62	
   63	If `git status --short` shows unrelated dirty or staged work, the coordinator records that fact in the audit context and avoids committing or reverting it. Dirty work does not automatically block read-only audit. Before mutation, however, the coordinator must specifically check whether `docs/tasklist.json` is itself dirty or staged with unrelated edits: `tasktool close` and `tasktool cancel` auto-commit scoped tracker/archive changes by default, and pre-existing tracker dirt can be folded into that lifecycle commit. Resolve or stash unrelated tracker dirt first; use `tasktool close --no-commit` only when the operator intentionally wants the tracker to remain staged.
   64	
   65	### 2. Batching and Delegation
   66	
   67	The skill must require coordinator-led batching when cleanup involves more than six candidate rows or spans more than one coherent theme:
   68	
   69	- Use one worker per coherent theme or per bounded batch of 4-6 rows.
   70	- Use `dispatching-parallel-agents` when batches are independent.
   71	- Workers may inspect evidence but must not edit files or run mutating tasktool commands.
   72	- Workers must return dossiers, not prose-only summaries.
   73	- A single coordinator must not review 20+ heterogeneous rows alone.
   74	
   75	Acceptable worker evidence sources include:
   76	
   77	- `tasktool show <id>`
   78	- `tasktool list --open`
   79	- `docs/specs/`, `docs/plans/`, `docs/handoffs/`
   80	- `docs/reviewer/`
   81	- `docs/archived-tasks/`
   82	- relevant source/docs paths named by the row
   83	- targeted `rg` searches
   84	- recent commits where needed
   85	
   86	Workers must not run:
   87	
   88	```bash
   89	tasktool close <id>
   90	tasktool cancel <id> --reason "..."
   91	tasktool set <id> ...
   92	tasktool note <id> ...
   93	tasktool ref <id> ...
   94	```
   95	
   96	### 3. Dossier Contract
   97	
   98	Every audited row must produce a dossier with this shape:
   99	
  100	```markdown
  101	## <id> — <title>
  102	
  103	**Recommended action:** keep | close | cancel | promote | uncertain
  104	**Evidence checked:** <commands/files/refs reviewed>
  105	**Rationale:** <why the evidence supports the recommendation>
  106	**Proposed command:** <exact tasktool command, or "none">
  107	**Confidence / risk notes:** <known gaps, ambiguity, or blast radius>
  108	```
  109	
  110	Action meanings:
  111	
  112	| Action | Meaning |
  113	|--------|---------|
  114	| `keep` | The row is still valid and should remain open. |
  115	| `close` | The work is truthfully done and evidence supports `tasktool close <id>`. |
  116	| `cancel` | The work is abandoned, superseded, invalid, intentionally not shipping, or no longer desired; use `tasktool cancel <id> --reason "..."`. |
  117	| `promote` | The row should become or feed a proper phase/slice/spec/plan before it can be resolved. |
  118	| `uncertain` | Evidence is incomplete or conflicting; do not mutate. |
  119	
  120	Age alone is never evidence for `close` or `cancel`.
  121	
  122	`promote` does not run a tasktool mutation during janitor cleanup. The coordinator records the promotion recommendation in the audit artifact and routes it into the normal Superstar spec/plan workflow if the user wants to pursue it.
  123	
  124	### 4. Coordinator Reconciliation
  125	
  126	The coordinator merges worker dossiers into grouped recommendations. Before presenting anything to the user, the coordinator must re-check every `close` and `cancel` recommendation against the cited evidence. Weak recommendations are downgraded to `uncertain`.
  127	
  128	The user-facing recommendation must group rows by action and include the exact commands proposed for approved mutation. The coordinator must ask for approval before running any mutating command.
  129	
  130	### 5. Mutation Discipline
  131	
  132	After approval, the coordinator applies changes only with tasktool commands:
  133	
  134	```bash
  135	tasktool close XNN
  136	tasktool cancel XNN --reason "..."
  137	```
  138	
  139	The skill must state:
  140	
  141	- `tasktool close XNN` is only for truthfully done work.
  142	- `tasktool cancel XNN --reason "..."` is for abandoned, superseded, invalid, or intentionally unshipped work.
  143	- `tasktool cancel` does not apply to task rows; non-cross lifecycle details remain owned by `tasklist-discipline`.
  144	- `tasktool close XNN` on a cross row still passes tasktool's landed-branch gate. If the row records an unlanded worktree branch, close is refused; do not improvise flags, and consult `tasklist-discipline` for any sanctioned override and required reason.
  145	- Before any `close` or `cancel`, confirm `docs/tasklist.json` is not itself dirty or staged with unrelated edits because close/cancel auto-commit scoped tracker/archive changes by default. Resolve or stash unrelated tracker dirt first; use `--no-commit` only for an intentional staged lifecycle package.
  146	- Apply changes in small batches.
  147	- Run `tasktool validate` and re-check open rows after each batch.
  148	- Preserve unrelated dirty/staged work.
  149	- Stop and report if tasktool refuses a mutation instead of hand-editing `docs/tasklist.json`.
  150	
  151	### 6. Audit Trail
  152	
  153	For substantial cleanup, the skill must leave or recommend a durable audit artifact unless the user explicitly requests chat-only output. The artifact should live under `docs/handoffs/` or another existing repo docs area chosen by local convention and record:
  154	
  155	- original row id and title
  156	- action recommended
  157	- evidence checked
  158	- command approved and run, if any
  159	- final state after mutation, including the archived-task path when closing or cancelling an `X*` row archives it
  160	- unresolved uncertainties
  161	
  162	The skill should avoid forcing a particular filename because cleanup may happen outside a formal spec/plan slice. A recommended default is:
  163	
  164	```text
  165	docs/handoffs/YYYY-MM-DD-tasktool-janitor-audit.md
  166	```
