Findings

F1 — `tasktool cancel` does not auto-commit and has no `--no-commit` flag; the skill and spec claim it does. Severity: important.
Both the spec (`docs/specs/...md:63`, `:145`) and the skill body the plan tells the implementer to write (`docs/plans/...md:242`, and the Mutation Rules section `:311`) state: "`tasktool close` and `tasktool cancel` auto-commit scoped tracker/archive changes by default … use `--no-commit` only when …". I checked the source:
- `tools/tasktool/cli.py:185` — the `cancel` parser accepts only `id`, `--reason`, `--cascade`, `--no-archive`. There is no `--no-commit`. `tasktool cancel … --no-commit` would error out.
- `tools/tasktool/commands.py:1371` `cmd_cancel` — it calls `_save` and `_git_stage(archive_path)` but never `_git_commit_scoped`. Cancel **stages** the tracker/archive but leaves them **uncommitted**. Only `cmd_close` (`commands.py:1342`) commits, gated by `no_commit`.
This is load-bearing, user-shipping content. An agent told "cancel auto-commits by default" will believe a cancel batch is committed when it has only left a dirty/staged index — exactly the failure the janitor workflow is meant to prevent. The string tests don't catch it (they only assert the token `"auto-commit"` appears once, satisfied by the `close` clause), so the inaccuracy ships silently. Correct the wording to: `close` auto-commits (opt out with `--no-commit`); `cancel` stages but does not commit and has no `--no-commit` — the operator commits the staged tracker/archive themselves.

F2 — Task 5 closeout omits the merge-back step, so `tasktool close X31` will be refused by the landed-branch gate. Severity: important.
Task 0 runs `tasktool start X31`, which creates a worktree on branch `wt-x31`. Cross-row close is landed-branch-gated — confirmed by `tools/tasktool/tests/test_close_gate.py:157` (`test_cross_item_with_unlanded_branch_is_gated`). Task 5 Step 4's prose says "Merge, close, and prune through normal tasktool lifecycle" and "Follow `subagent-driven-development` closeout", but the command block (`docs/plans/...md:474-477`) shows only `tasktool close X31` / `tasktool worktree prune X31` — no merge of `wt-x31` into `main`. As written the close will refuse with "not landed … --allow-unlanded". Add the explicit merge-back step before `tasktool close` (per `finishing-a-development-branch` Option 1 mechanics that `subagent-driven-development` defers to), and state that `--allow-unlanded` is NOT the path here. The Expected note ("closes only after the implementation is landed") acknowledges the gate but never shows how landing happens.

F3 — Version-bump step doesn't account for the bump→re-sync gotcha. Severity: minor.
Task 5 Step 3 correctly asks the bump question and commits the bump separately. But `scripts/bump-version.sh` rewrites the plugin mirror and version strings, and the pre-commit hook can block the bump commit until `install.sh` / `install.sh --hook --force` is re-run (a known operational detail in this fork). Since the bump is optional and user-gated this is minor, but a one-line pointer to re-running the installer after the bump would save a failed commit.

F4 — Dossier header dash differs between spec and skill. Severity: nit.
Spec uses `## <id> — <title>` (em dash, `:101`); the skill content in the plan uses `## <id> - <title>` (hyphen, `:269`). The test only pins the field labels, so neither breaks. Pick one for consistency.

F5 — Task 0 assumes the `X31` cross row already exists in `docs/tasklist.json`. Severity: minor.
The Scheduling Contract and `tasktool start X31` presuppose the row exists. `tasktool brief X31` in Step 1 will surface a missing row by failing, which is an acceptable implicit gate, so this is low-risk — just worth an explicit "Expected: brief prints the existing X31 row" so a missing row is caught before `start`.
