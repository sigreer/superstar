  154	from __future__ import annotations
  155	
  156	from dataclasses import dataclass
  157	from enum import Enum
  158	from pathlib import Path
  159	
  160	
  161	class ArtifactError(RuntimeError):
  162	    pass
  163	
  164	
  165	class ArtifactKind(str, Enum):
  166	    SPEC = "spec"
  167	    PLAN = "plan"
  168	    HANDOFF = "handoff"
  169	    REVIEWER = "reviewer"
  170	    ARCHIVE = "archive"
  171	
  172	
  173	KIND_PREFIXES = {
  174	    ArtifactKind.SPEC: "docs/specs/",
  175	    ArtifactKind.PLAN: "docs/plans/",
  176	    ArtifactKind.HANDOFF: "docs/handoffs/",
  177	    ArtifactKind.REVIEWER: "docs/reviewer/",
  178	    ArtifactKind.ARCHIVE: "docs/archived-tasks/",
  179	}
  180	
  181	
  182	@dataclass(frozen=True)
  183	class NormalizedArtifact:
  184	    kind: ArtifactKind
  185	    relative_path: str
  186	    invocation_path: Path
  187	    write_path: Path
  188	    exists_in_write_root: bool
  189	
  190	
  191	def _inside(root: Path, path: Path) -> bool:
  192	    try:
  193	        path.resolve().relative_to(root.resolve())
  194	        return True
  195	    except ValueError:
  196	        return False
  197	
  198	
  199	def _relative_to_invocation(invocation_root: Path, raw_path: Path) -> tuple[str, Path]:
  200	    candidate = raw_path.expanduser()
  201	    if not candidate.is_absolute():
  202	        candidate = invocation_root / candidate
  203	    candidate = candidate.resolve()
  204	    if not _inside(invocation_root, candidate):
  205	        raise ArtifactError(f"artifact path is outside repository: {raw_path}")
  206	    return candidate.relative_to(invocation_root.resolve()).as_posix(), candidate
  207	
  208	
  209	def normalize_artifact_path(
  210	    *,
  211	    invocation_root: Path,
  212	    write_root: Path,
  213	    raw_path: Path,
  214	    kind: ArtifactKind,
  215	    allow_missing: bool,
  216	) -> NormalizedArtifact:
  217	    relative, invocation_path = _relative_to_invocation(invocation_root, raw_path)
  218	    prefix = KIND_PREFIXES[kind]
  219	    if not relative.startswith(prefix):
  220	        raise ArtifactError(f"{kind.value} artifacts must live under {prefix}")
  221	    write_path = (write_root / relative).resolve()
  222	    exists_in_write = write_path.exists()
  223	    if not allow_missing and not exists_in_write:
  224	        if invocation_path.exists() and invocation_root.resolve() != write_root.resolve():
  225	            raise ArtifactError(
  226	                "artifact exists in invocation checkout but not authoritative checkout; "
  227	                "create or copy it to the authoritative checkout before registering"
  228	            )
  229	        raise ArtifactError(f"artifact path does not exist: {relative}")
  230	    return NormalizedArtifact(
  231	        kind=kind,
  232	        relative_path=relative,
  233	        invocation_path=invocation_path,
  234	        write_path=write_path,
  235	        exists_in_write_root=exists_in_write,
  236	    )
  237	```

### docs/specs/2026-05-21-X17-transactional-spec-plan-artifacts-design.md

    1	# X17 — transactional spec and plan artifact handling
    2	
    3	**Status:** spec
    4	**Tasktool ID:** X17 (cross-cutting)
    5	**Date:** 2026-05-21
    6	
    7	## Problem
    8	
    9	The current Superstar workflow intentionally allows spec, plan, handoff, and reviewer-chain artifacts to be produced on the authoritative checkout (`main`). That is the right place for durable planning state: later agents need one canonical tasklist and one canonical set of workflow artifacts.
   10	
   11	The failure mode is that tasktool only owns `docs/tasklist.json`. A spec/planning agent can create or revise files under `docs/specs/`, `docs/plans/`, `docs/handoffs/`, `docs/reviewer/`, and `docs/archived-tasks/`, while separately updating `docs/tasklist.json` through `tasktool create`, `tasktool ref`, `tasktool archive-phase`, or manual edits. If those files are left unstaged or only partly staged, the next routed mutation fails with:
   12	
   13	> authoritative docs/tasklist.json has unstaged changes; commit, stash, or normalise them before running tasktool
   14	
   15	That guard is correct. It prevents a later `tasktool start` or `tasktool close` from writing over unattributed authoritative task state. But it catches the problem late, after the checkout has already accumulated loose workflow state.
   16	
   17	The recent X15/X16 collision is the concrete symptom: X15 spec/plan/tracker state was present in the authoritative checkout while another agent tried to run X16 lifecycle commands. Tasktool blocked the X16 mutation, but it did not provide a first-class way for the X15 planning agent to create, register, validate, stage, and optionally commit its workflow artifacts as one durable transaction.
   18	
   19	## Goals
   20	
   21	1. Add tasktool commands that make spec/plan/handoff/reviewer artifact registration transactional with the tasklist row they belong to.
   22	2. Make the safe path ergonomic enough that agents do not hand-edit `docs/tasklist.json` or leave orphan dated docs behind.
   23	3. Preserve the current model where planning artifacts live on the authoritative checkout and implementation still runs from isolated worktrees.
   24	4. Fail early when the authoritative checkout already has unsafe tasklist or artifact dirt.
   25	5. Update workflow skills so spec/plan agents use the new commands instead of treating artifact staging as an afterthought.
   26	
   27	## Non-goals
   28	
   29	- Generating spec or plan prose. Agents still write the documents; tasktool owns registration, validation, staging, and optional commit boundaries.
   30	- Replacing external-review. Reviewer-chain generation remains owned by the external-review tooling. Tasktool only registers and validates the chain artifact after it exists.
   31	- Auto-merging unrelated dirty state. The command refuses ambiguous checkouts rather than guessing what belongs to the current work item.
   32	- Moving planning off `main`. This spec keeps durable planning state on the authoritative checkout by design.
   33	- Changing implementation worktree creation or merge-back rules.
   34	
   35	## Design
   36	
   37	### 1. `tasktool artifact add`
   38	
   39	Add a new mutating command:
   40	
   41	```bash
   42	tasktool artifact add <id> --kind spec --path docs/specs/...
   43	tasktool artifact add <id> --kind plan --path docs/plans/...
   44	tasktool artifact add <id> --kind handoff --path docs/handoffs/...
   45	tasktool artifact add <id> --kind reviewer --path docs/reviewer/<chain-dir>/
   46	tasktool artifact add <id> --kind archive --path docs/archived-tasks/...
   47	```
   48	
   49	Semantics:
   50	
   51	- Routes through the configured authoritative checkout using the existing `_write_context` path.
   52	- Refuses if the authoritative `docs/tasklist.json` has unstaged changes, using the existing unsafe-dirty guard.
   53	- Resolves `<id>` through the same `_find_item` path used by `tasktool ref`, so short IDs behave consistently.
   54	- Requires `--path` to be repository-relative after normalization. Absolute paths are accepted only if they resolve inside the invocation repository; they are stored as relative paths.
   55	- Requires the target path to exist, except `--kind spec|plan|handoff --allow-missing` for the narrow case where the row is being reserved before the agent writes the file. The default is strict existence checking.
   56	- Adds the path to `item.refs` if not already present. For phase/slice-specific model fields that already exist, it also updates the typed field:
   57	  - `--kind spec` updates `spec_path` when the item has that field.
   58	  - `--kind plan` updates `plan_path` when the item has that field.
   59	  - `--kind reviewer` updates `reviewer_chain` for slices and `phase_reviewer_chain` for phases when applicable.
   60	  - Cross-cutting items continue to use `refs` only, because they intentionally have no typed spec/plan fields today.
   61	- Saves `docs/tasklist.json`, stages it, and stages the artifact path itself with `git add`.
   62	- Prints the registered relative path and whether it was newly added or already present.
   63	
   64	This command is the direct replacement for ad hoc `tasktool ref X --add <path>` during planning. `tasktool ref` remains available for generic references, but workflow skills should prefer `artifact add` for spec/plan/handoff/reviewer paths.
   65	
   66	### 1a. Path resolution and routed writes
   67	
   68	The command must preserve the existing tasktool distinction between invocation root and write root:
   69	
   70	- **Invocation root**: the checkout where the user ran `tasktool`.
   71	- **Write root**: the authoritative checkout selected by `_write_context`.
   72	- **Stored path**: always a repository-relative POSIX path, independent of which checkout invoked the command.
   73	
   74	Artifact paths are interpreted as follows:
   75	
   76	1. A relative `--path` is resolved against the invocation root for user intent and validated to stay inside that checkout.
   77	2. An absolute `--path` is accepted only if it resolves inside the invocation root.
   78	3. The stored path is the path relative to the invocation root.
   79	4. Existence is checked at the write root for normal planning artifacts, because durable spec/plan/handoff/reviewer artifacts are required to live on the authoritative checkout.
   80	5. If the path exists only in a linked implementation worktree and not in the write root, `artifact add` refuses with:
   81	
   82	   ```text
   83	   artifact exists in invocation checkout but not authoritative checkout; create or copy it to the authoritative checkout before registering
   84	   ```
   85	
   86	6. Staging always happens in the write root. The command runs `git add docs/tasklist.json <stored-path>` from the write root.
   87	
   88	This deliberately does not copy artifacts from an implementation worktree into `main`. Copying would hide the boundary that caused the original problem. Planning artifacts are authoritative workflow state; if they are meant to be durable, they must already exist in the authoritative checkout before they are registered without `--allow-missing`.
   89	
   90	### 2. `tasktool artifact status`
   91	
   92	Add a read-only diagnostic command:
   93	
   94	```bash
   95	tasktool artifact status [<id>] [--format text|json] [--strict]
   96	```
   97	
   98	When `<id>` is omitted, it scans the active tasklist and the workflow artifact directories. It reports:
   99	
  100	- Referenced artifact paths that do not exist.
  101	- Existing dated spec/plan/handoff files that are not referenced by any tasklist row.
  102	- Reviewer-chain directories under `docs/reviewer/` that are not referenced by any row.
  103	- Workflow artifact files that are unstaged while `docs/tasklist.json` is staged or clean.
  104	- Referenced artifact paths for the scoped row that exist but are untracked or unstaged.
  105	- `docs/tasklist.json` changes that are unstaged while workflow artifacts are present.
  106	
  107	When `<id>` is supplied, the report is limited to that row and its references.
  108	
  109	This command does not mutate. It gives agents and hooks a cheap preflight for "will this planning state surprise the next tasktool mutation?"
  110	
  111	For row-scoped checks, `artifact status <id> --strict` must report referenced artifacts that exist but are untracked or unstaged. That includes the common sequence `prepare --spec <future-path>`, write the spec file, then forget to stage it. The diagnostic code for this case is `referenced-artifact-unstaged`, and the message must name the path plus the exact next command:
  112	
  113	```text
  114	referenced artifact exists but is not staged: docs/specs/...; run tasktool artifact add <id> --kind spec --path docs/specs/... or tasktool artifact commit <id> --message ...
  115	```
  116	
  117	Exit behavior:
  118	
  119	- Without `--strict`, exit 0 after printing the report, even when problems are present.
  120	- With `--strict`, exit 1 when any problem is present and exit 0 when the report is clean.
  121	- `--format json` returns:
  122	
  123	  ```json
  124	  {
  125	    "ok": false,
  126	    "problems": [
  127	      {
  128	        "severity": "error",
  129	        "code": "missing-referenced-artifact",
  130	        "id": "X17",
  131	        "path": "docs/specs/example.md",
  132	        "message": "referenced artifact path does not exist"
  133	      }
  134	    ]
  135	  }
  136	  ```
  137	
  138	Initial severities are `error` and `warning`. `--strict` fails on both unless a future flag explicitly narrows the threshold; that narrower flag is out of scope for this slice.
  139	
  140	### 3. `tasktool artifact commit`
  141	
  142	Add an optional transaction closeout command:
  143	
  144	```bash
  145	tasktool artifact commit <id> --message "X17: add transactional artifact spec"
  146	```
  147	
  148	Semantics:
  149	
  150	- Routes to the authoritative checkout.
  151	- Refuses if `docs/tasklist.json` has unstaged changes before the transaction begins.
  152	- Checks referenced artifact paths and refuses missing references.
  153	- Stages `docs/tasklist.json` plus every referenced existing artifact path for the row.
  154	- Runs `artifact status <id> --strict` after staging so prepared-but-newly-written artifacts are allowed to become part of the transaction.
  155	- Runs a target-slug orphan scan and refuses unreferenced dated artifacts that appear to belong to the same work item.
  156	- Refuses if the staged diff contains paths outside:
  157	  - `docs/tasklist.json`
  158	  - `.tasktool/config.json`
  159	  - `docs/specs/`
  160	  - `docs/plans/`
  161	  - `docs/handoffs/`
  162	  - `docs/reviewer/`
  163	  - `docs/archived-tasks/`
  164	- Creates a git commit with the supplied message.
  165	- Does not push.
  166	
  167	The ordering is intentional. `artifact commit` is allowed to remediate `referenced-artifact-unstaged` by staging referenced existing artifacts itself. It still refuses missing references, unrelated staged paths, and post-staging strict-status problems.
  168	
  169	This is deliberately separate from `artifact add`. Some agents may need multiple review iterations before committing. The important property is that tasktool can now close the planning transaction when the spec/plan/review bundle is ready.
  170	
  171	Target-slug matching is deterministic:
  172	
  173	- The command derives the target slug from the first referenced spec or plan filename for the row by removing the leading `YYYY-MM-DD-` date and the leading task ID segment, then removing a trailing `-design` for specs and `-prompt` for handoffs.
  174	- For `docs/reviewer/`, it treats directories containing that slug and the review kind suffix as belonging to the row.
  175	- For `docs/specs/`, `docs/plans/`, and `docs/handoffs/`, it treats dated filenames containing both the row ID and the target slug as belonging to the row.
  176	- For `docs/archived-tasks/`, it only considers paths explicitly referenced by the row. Phase archive generation remains owned by `archive-phase`; archive files are not guessed from slug alone.
  177	
  178	If no target slug can be derived, `artifact commit` skips slug-based orphan refusal and relies on `artifact status <id> --strict` plus the staged-path allowlist. This keeps commit safe without making old or unusual task rows uncommittable.
