Findings

F1 — File Scope targets the generated mirror, not the source the tests read. Severity: blocking.
The spec's File Scope (lines 80–87) directs all skill edits to `plugins/superstar/skills/<name>/SKILL.md`. But the test harness this slice extends — `tools/tasktool/tests/test_skill_tasktool_lifecycle_docs.py:6-10` — computes `ROOT = Path(__file__).resolve().parents[3]` (the repo root) and reads skills from `ROOT / "skills" / name / "SKILL.md"`, i.e. the **top-level** `skills/` tree, not `plugins/superstar/skills/`. The two trees are distinct file copies (different inodes; currently identical content), and `plugins/superstar/skills/` is a **generated mirror**: `scripts/publish-to-local-codex.sh:80` runs `rsync -a --delete --exclude tests/ … "$REPO_ROOT/skills/" "$SOURCE/skills/"` (and `publish-to-local-claude.sh` keys off top-level `skills/` paths). Consequences if implemented as written:
- Editing only `plugins/superstar/skills/...` leaves the test-read files (`skills/...`) unchanged → the new §4 regressions fail and the Acceptance command (line 102) fails.
- Any mirror-only edits are reverted by the next publish's `rsync --delete`.
- The spec is internally inconsistent: the fixtures it does name (`tools/tasktool/tests/fixtures/p5_s3_*.txt`, line 74) and the test module live under the **source** tree, while the skill edits point at the **mirror**.
Fix: File Scope must name `skills/subagent-driven-development/SKILL.md`, `skills/tasklist-discipline/SKILL.md`, and (conditional) `skills/finishing-a-development-branch/SKILL.md`, `skills/using-git-worktrees/SKILL.md` — and state that `plugins/superstar/skills/` is regenerated by the publish scripts, not hand-edited.

F2 — "Merge-back through `finishing-a-development-branch`" collides with that skill's bundled prune, which must run after close. Severity: important.
D1 / Required Behavior §1 route the pre-close merge-back "through `[[finishing-a-development-branch]]`" and cite its "local merge option 1." But Option 1 (`skills/finishing-a-development-branch/SKILL.md:119-157`) ends by running Cleanup Step 6, whose default is `tasktool worktree prune <slice-id>` — and prune's guard 1 requires a **terminal status** (`commands.py:3220-3226`: refuses unless the slice is `done`/`cancelled`). Since merge-back is specified to happen *before* `tasktool close`, an agent that follows `finishing-a-development-branch` Option 1 literally will hit the prune slice-done refusal pre-close — the exact "hit the refusal late and misread it as a tooling problem" failure this slice exists to prevent. The spec lists prune as a separate post-close step (§1 final bullet) but never tells the implementer to carve Step 6 out of the merge-back reference. Recommend promoting the `finishing-a-development-branch` edit from "conditional" to required, and specifying that merge-back uses only Option 1's merge mechanics (Step 5), deferring prune to after close.

F3 — Phase-end `finishing-a-development-branch` invocation is left inconsistent with per-slice merge-back. Severity: important.
The existing slice flow merges nothing at slice end and invokes `[[finishing-a-development-branch]]` once at phase end (`subagent-driven-development/SKILL.md:68` and diagram node line 130) to merge+clean all already-closed slices. Moving merge-back+prune to per-slice means that at phase end the slices are already merged and pruned: Option 1 finds nothing to merge and Step 6 prune refuses with "no recorded worktree to prune" (`commands.py:3209-3213`). The spec scopes edits to the slice-end sequence only and does not say what the phase-end `finishing-a-development-branch` step now does. This leaves a second, contradictory closeout path in the same skill. The spec should state the intended phase-end behavior under the new per-slice flow (e.g. phase-end finishing reduces to branch finalization / a no-op for already-pruned slices).

F4 — "Out of Scope: docs-only, no version bump" contradicts the binding fork policy for skill changes. Severity: important.
Line 110 asserts "docs-only changes do not require a version bump." But CLAUDE.md's binding "Releases & version bumps" section requires asking the user about a bump "before committing finished work that ships to users — skill changes … anything in `plugins/superstar/`, `skills/`" and exempts only "Docs-only changes, in-progress work on feature branches, and tasktool tracker mutations." SKILL.md edits under `skills/` ship to users and are *not* "docs-only" in that policy's sense. As written, the spec could lead the closeout agent to skip the required bump prompt. Recharacterize: at slice close the agent must still surface the bump question per CLAUDE.md (the spec may note the recommended answer, but cannot declare it out of scope).

F5 — Diagram currently has no per-slice prune node. Severity: minor.
§1 requires the process diagram to show "post-slice review ready -> merge back -> `tasktool close` -> non-force prune/finish branch." Today the diagram's slice path (`subagent-driven-development/SKILL.md:154-156`) goes review-ready → close → "Last slice in phase?", with prune/finish appearing only in the phase-terminal `finishing-a-development-branch` node (line 130). The implementer must add *two* new nodes (merge-back and a per-slice prune), not just one. Spell that out so the diagram and prose don't drift.

F6 — Ordering assertion in §4 can match the wrong `tasktool close <slice-id>` occurrence. Severity: minor.
The proposed test "merge-back appears after post-slice review readiness and before `tasktool close <slice-id>`" relies on string position, but `tasktool close <slice-id>` appears multiple times in the skill (slice-end prose line 62, diagram lines 154-155, plus a red-flag row). The existing `test_subagent_driven_development_has_integrate_main_checkpoint` (`test_skill_…:193-201`) uses bare `text.index(...)` and so anchors on the *first* occurrence. The new test must anchor on the slice-end prose occurrence deliberately (a nearby stable substring), or it will pass/fail on the wrong region. Note this in §4.

F7 — "integrate current main" is restated as if new in D1. Severity: nit.
D1 enumerates "scope preflight, integrate current main, post-slice external review, merge-back…". The integrate-current-main checkpoint already exists (`subagent-driven-development/SKILL.md:58`, pinned by `test_…_has_integrate_main_checkpoint`). D1 should say "preserve the existing integrate-current-main checkpoint and insert merge-back after review" so the implementer doesn't duplicate the step.
