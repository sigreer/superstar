1. Findings

F1 — Severity: blocking  
The plan misses the spec-required `brief` / `show` cancellation-reason surfacing. The spec requires active cancelled rows to surface the cancellation reason and tests both active cancelled rows and archived-X not-found behavior (`docs/specs/2026-05-23-X22-cancelled-status-design.md:223-224`, `:321-324`). The plan’s file list does not include `tools/tasktool/brief.py` (`docs/plans/2026-05-23-X22-cancelled-status.md:18-28`), and Task 13 explicitly says `cmd_show` is unchanged (`:1137`). Current `cmd_show` only prints raw notes (`tools/tasktool/commands.py:1399-1437`) and `cmd_brief` delegates to `brief.py` (`:1859-1863`), so this requirement will not be implemented.

F2 — Severity: important  
The schema plan does not satisfy the spec’s independent JSON-schema rejection gate for task rows. The spec explicitly requires a JSON-schema test where raw task JSON with `status="cancelled"` fails validation, independently from semantic `validate_project()` rejection (`docs/specs/2026-05-23-X22-cancelled-status-design.md:73-79`, `:312-315`). The plan only introspects generated enum lists (`docs/plans/2026-05-23-X22-cancelled-status.md:153-170`), which is weaker than validating an instance and can miss broken schema wiring around required paths or fixture shape.

F3 — Severity: important  
The `cmd_set` defense-in-depth requirement is missing. The spec says `cmd_set` must explicitly reject `Status.CANCELLED` with a hint to use `tasktool cancel`, even if future CLI choices are widened (`docs/specs/2026-05-23-X22-cancelled-status-design.md:98-100`, `:279-282`). Task 9 only says not to add `cancelled` to CLI choices and tests setting `ready|in_progress|done` from an already-cancelled row (`docs/plans/2026-05-23-X22-cancelled-status.md:794-798`, `:780`). Add a direct `cmd_set(..., status="cancelled")` test and implementation branch before normal status mutation.

F4 — Severity: important  
`cmd_cancel` notification coverage is too weak. The spec requires notifier invocation with `status="cancelled"` exactly once per cancel call and once per cascaded child (`docs/specs/2026-05-23-X22-cancelled-status-design.md:236-240`, `:327-330`). The plan pins generic notifier formatting in Task 6 (`docs/plans/2026-05-23-X22-cancelled-status.md:453-465`) and tests archive-phase notification in Task 11 (`:948-957`), but Task 7 and Task 8 do not assert cancel/cascade notification counts or payloads.

F5 — Severity: minor  
The final live CLI smoke test mutates the real authoritative tracker by creating and cancelling a new cross-cutting row (`docs/plans/2026-05-23-X22-cancelled-status.md:1223-1233`). That creates durable archive noise as part of verification. Prefer a temp fixture repo or a clearly named ad-hoc smoke row with an explicit cleanup/archive expectation. Also, `tasktool list | grep -i cancel` may not prove the default auto-archived X path, because the row leaves active `cross_cutting`.
