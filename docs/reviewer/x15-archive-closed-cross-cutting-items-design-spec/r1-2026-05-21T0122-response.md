# Review: X15 - Archive closed cross-cutting items (spec)

## 1. Findings

**F1 — Severity: important.** Section 3 contradicts itself on `--no-archive` for non-cross items. The sentence "For slices and phases, `--no-archive` has no effect and should be rejected with a clear error if supplied" mixes "no effect" with "rejected". Error handling §Error handling and test #5 both confirm rejection. Tighten §3 to a single rule: "supplying `--no-archive` on a non-cross close fails."

**F2 — Severity: important.** Component boundaries miss two files that are touched by adding a top-level `archived_cross_cutting` array:
- `tools/tasktool/migrate.py` — `_PROJECT_COLLECTIONS` at line 12 is `("phases", "cross_cutting", "archived_phases")`; the new collection needs migrate semantics or migrate diverges from authoritative.
- `tools/tasktool/schema_gen.py` — generates the JSON schema (line 113-120 today wires `cross_cutting`); the new field needs a schema entry or `validate --strict-format` will be incomplete.

Both should be called out, even if the change is "add the field analogously to archived_phases."

**F3 — Severity: important.** Goal #5 promises to "document the tasklist data-shape change for downstream consumers such as AGS sidebar tasklist views." Section 7 says the note goes "in the spec, plan, or handoff" — none of those are discoverable by an AGS developer who doesn't know X15 exists. Specify a durable destination: either a section in `skills/tasklist-discipline/SKILL.md`, a `CHANGELOG.md` entry, or a top-of-`docs/tasklist.json` README. "Burying in this spec" is not a deliverable.

**F4 — Severity: important.** Close path side effects are under-specified. `cmd_archive_phase` in `tools/tasktool/commands.py:1095-1174` stages only the new archive file (`_git_stage(write_root, archive_path)`) — it does not stage `docs/tasklist.json`. The spec's archive-cross rule §4 says "save, stage the touched files" (plural), while the default-close-archive path §2 says nothing about staging. Two questions to resolve:
- Should both paths stage only the archive .md, only the tasklist.json, or both?
- Should they match `archive-phase`'s actual behavior (stage archive file only)?

Without a decision, implementers will guess.

**F5 — Severity: important.** §2 step 5 ("Write `<archive>.md` with the full X-item JSON") happens BEFORE step 6/7 mutate the in-memory project. `cmd_archive_phase` deliberately validates the mutated project BEFORE filesystem writes (`commands.py:1167-1173`). The X15 spec sequence inverts that ordering risk — if validation later rejects (e.g. duplicate ID, malformed pointer), the .md file is already on disk and `docs/tasklist.json` is untouched, leaving an orphan archive file. Re-order to match the proven archive-phase pattern: build content in memory → mutate project → validate → write file → save → stage.

**F6 — Severity: minor.** Error message in §Error handling: `cross-cutting X15 not found in active tasklist; it may already be archived`. Today `_find_item` raises through `_resolve_id` with a generic "not found" message. Spec should explicitly say "extend `_find_item` (or a wrapper in `cmd_close`) to detect presence in `archived_cross_cutting` and produce the friendlier message," otherwise this error is unlikely to appear as written.

**F7 — Severity: minor.** Notification path is asymmetric. §4 says archive-cross "emits the existing done notification path if appropriate," but §2 (default close) is silent. Today's `cmd_close` at `commands.py:616` calls `_notify_status(... status=Status.DONE ...)`. Spec should confirm: default-close-archive fires the existing done notification exactly once; archive-cross of an already-done item either fires it again or does not (pick one). Test #1 should assert which.

**F8 — Severity: minor.** No `unarchive-cross` is in scope, yet the archive file header (§5, line 123) reads `## Full cross-cutting JSON (for tasktool unarchive)`. That mirrors the phase archive convention (`commands.py:1152`), and the unarchive command is also absent there, so this is a pre-existing forward reference rather than a new defect. Worth a one-line note in Non-goals: "Unarchive command is out of scope; the embedded JSON enables it later, but no unarchive subcommand ships in this slice."

**F9 — Severity: minor.** Ordering of `archived_cross_cutting` is unspecified. `archived_phases` is appended in close order today (`commands.py:1163`) and rendered in that order. Spec should say either "append-only" or "sort by archived_date on render"; otherwise rendering output is non-deterministic across migrate paths.

**F10 — Severity: minor.** No test covers `tasktool list --kind cross` exclusion of archived items. Test #8 only covers `render`. Add an explicit list-command test or state it's implicit because archived items leave `cross_cutting`.

**F11 — Severity: minor.** `brief.py:12` resolves items from `p.cross_cutting` only. Spec is silent on whether `tasktool brief X15` after archival should (a) error with "archived," (b) read from the archive file, or (c) work via the pointer's title only. Most consistent with phase archives is (a). State it.

**F12 — Severity: nit.** Schema version: `SCHEMA_VERSION = 1` in `model.py:6`. Adding `archived_cross_cutting` with default `[]` is backwards-compatible and should not bump the schema. Spec should say so explicitly so implementers don't guess.

**F13 — Severity: nit.** §5 archive header omits `refs:` from the summary block (only embedded in JSON). Phase archive summary surfaces refs/spec/plan paths inline. Consistency is low cost: render `refs` and `notes` headings in the summary, matching phase archive style.

**F14 — Severity: nit.** Title casing: §6 uses `## Archived cross-cutting` while existing render uses `## Archived phases` and `## Cross-cutting (`X*`)`. Suggest `## Archived cross-cutting (`X*`)` for symmetry.

## 2. Open questions / assumptions

- Q1 (F4): Which files does close-archive and archive-cross stage?
- Q2 (F7): Does archive-cross of an already-done X-item re-emit the done notification?
- Q3 (F11): Does `brief X<id>` work on archived items?
- Q4 (F3): Where does the data-shape note live so AGS developers can find it?
- A1 (assumed): No schema_version bump; `archived_cross_cutting` defaults to `[]` and legacy load remains compatible. Confirmed by `serialize.py:89` pattern.

## 3. Suggested document edits

- §2 (Default close behavior): Re-order to (1) build archive content in memory, (2) mutate project state, (3) validate project, (4) write archive file, (5) save tasklist, (6) stage, (7) notify — matching `cmd_archive_phase`.
- §3: Replace "has no effect and should be rejected" with "is rejected with `--no-archive is only valid for cross-cutting items`."
- §4: Specify exact files staged.
- §5: Add `refs` and `notes` to the human summary above the JSON block; explicitly say the embedded JSON is produced by `dumps_canonical` (or a shared helper) so ordering matches `tasklist.json` exactly.
- §6: Rename heading to `## Archived cross-cutting (`X*`)`; specify ordering rule.
- §7: Replace "spec, plan, or handoff" with a concrete destination (`skills/tasklist-discipline/SKILL.md` section or a new `docs/tasklist-data-shape.md`).
- Component boundaries: add `migrate.py` and `schema_gen.py`; note `brief.py` policy.
- Non-goals: add explicit "no `unarchive-cross` command" line.
- Testing: add a list-command test or note coverage rationale; add an atomicity test (validation failure leaves no orphan archive file on disk) covering F5.
