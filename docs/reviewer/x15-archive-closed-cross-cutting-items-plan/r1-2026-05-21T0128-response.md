# Plan review — X15 archive closed cross-cutting items

## Findings

**F1 — Missing brief.py work despite spec carving it out.** Severity: important
The spec (`docs/specs/2026-05-21-X15-...md` §Component boundaries and §6) explicitly states `tasktool brief X15` after archival must fail with the same active-tasklist-not-found semantics as archived phases, and lists `tools/tasktool/brief.py` as an owning module. The plan's File Structure and tasks omit `brief.py` entirely. If `brief()` falls through to a different error today, the spec contract isn't satisfied. Add either (a) a Task touching `brief.py` with a test, or (b) a verified assertion that current `brief()` already raises the right error for an unknown ID (i.e. that an archived X-item is indistinguishable from an unknown one) and a regression test that pins this behaviour.

**F2 — Several spec tests not enumerated in plan.** Severity: important
Spec §Testing lists 15 tests. The plan omits at least:
- #5 `test_close_no_archive_rejects_non_cross_items` (plan only adds the production check, no test).
- #9 `test_archive_cross_preserves_full_json` (only weakly covered by `'"id": "X1"' in ...read_text()` — does not assert refs/notes survive).
- #10 `test_legacy_tasklist_without_archived_cross_cutting_loads`.
- #11 `test_list_kind_cross_excludes_archived_items`.
- #12 `test_archive_cross_atomicity_no_orphan_file_on_validation_failure` (this is the load-bearing atomicity gate the spec calls out and the plan does not reproduce).
Add these as concrete steps; otherwise the implementation can pass the plan and still miss spec acceptance.

**F3 — Friendlier "already archived" close error is hand-waved.** Severity: important
Spec error-handling section says `tasktool close X15` where X15 is already archived must fail with `cross-cutting X15 not found in active tasklist; it may already be archived`, and `archive-cross` must say `cross-cutting X15 is already archived`. The plan addresses only the second case (inside `_archive_cross_at_root`). For the close path, Task 3 Step 6 only says "Add a helper or wrapper check so close and archive-cross produce the friendlier already-archived message" — no test, no code location, no error string. `_find_item` doesn't know about `archived_cross_cutting`, so this needs an explicit precheck in `cmd_close` before `_find_item` runs. Specify it, and add a test that pins the exact message.

**F4 — Plan deletes the existing `cmd_close` `_save` implicitly.** Severity: important
`commands.py:586-616` currently ends with `_save(write_root, p); _notify_status(...)`. The plan's Task 3 Step 5 shows the new shape with archive then `_save` then `_git_stage` then `_notify_status`, but never says "replace the existing `_save(write_root, p)`". An executor following Step 5 literally could end up with two `_save` calls or duplicate `_notify_status`. Reword Step 5 as a unified diff/replacement showing the existing tail being replaced, not augmented.

**F5 — Render assertion will pass for the wrong reason.** Severity: minor
`test_render_shows_archived_cross_section` (Task 2 Step 2) asserts `"**X1**" in out` and `"**X2**" in out`. In current `render.py:72,77`, both active cross items and archived phase pointers render as `**{id}**`, so once the archived cross section is added it will also be `**X2**`. The test would pass even if the archived section heading was missing, because `**X2**` could appear in the active section if the production code accidentally left it there. The heading assertion (`"## Archived cross-cutting (`X*`)"`) does catch the right thing, but consider also asserting that X2 appears *after* the archived heading and *not* in the active cross section (split the rendered output around the heading and assert membership in each half). This raises confidence that archival actually removes from `cross_cutting`.

**F6 — Inconsistent dash/hyphen in archive headings.** Severity: minor
Phase archive (`commands.py:1133`) renders `f"# {phase_id} — {phase.title}"` with em-dash. Plan's `_archive_cross_at_root` uses ASCII hyphen `f"# {item.id} - {item.title}"`. The spec example also uses `-`. Either is fine, but the divergence between phase and cross archive formats is unmotivated and will look like a typo to a future reader. Decide one and apply consistently, or call out the choice in a comment.

**F7 — `_CROSS_RE` and `_check_date` signatures assumed without verification.** Severity: minor
Plan's `_check_archived_cross` calls `_check_id(c.id, _CROSS_RE, scope)` and `_check_date(c.archived_date, scope, "archived_date")`. Neither symbol/signature is shown to exist in `validate.py`. If `_check_date` has a different parameter order (e.g. `(scope, value)` or no third "field name" argument) the implementer will silently bend the helper. Add a one-line note: "verify helper signatures in validate.py before using; adapt if names differ."

**F8 — Migration plan under-specifies `_apply_collection` wiring.** Severity: minor
Task 1 Step 5 says "Add `_diff_collection` and `_apply_collection` calls for `archived_cross_cutting`, using `ArchivedCrossCutting`." It doesn't show the actual block to mirror in `_apply_local` (visible at `migrate.py:226-239`). For an implementer following the plan top-to-bottom, this is enough to extrapolate but is the only place in the plan where a code change is described in prose instead of being shown. Consider showing the mirror block for symmetry with how `_diff_project` is treated.

**F9 — Setup `tasktool start X15` claim is unverified.** Severity: minor
Execution Setup Step 1 says `tasktool start X15` may reject "because crosscuts are not startable in this version" and offers `tasktool set X15 --status in_progress` as a fallback. Worth verifying: I see `cmd_close` accepting `kind == "cross"` without a gate (`commands.py:597`); whether `cmd_start` accepts cross-cutting wasn't checked. If it does support crosscuts, the fallback paragraph is noise. If it doesn't, say so definitively rather than "if rejects, do X".

**F10 — Plan close-of-X15 step uses `--reviewer-chain` for a cross-cutting item.** Severity: nit
Task 5 Step 4 closes X15 with `--reviewer-chain` set. Cross-cutting close has no review gate (`commands.py:597`), so the flag is silently accepted but does nothing. Either drop the flag or note explicitly that it is being recorded for paper-trail only.

**F11 — Archive JSON shape differs from spec example.** Severity: nit
Spec §5 shows the archived JSON as a bare X-item object (`{"closed": ..., "id": "X15", ...}`). Plan wraps it in a `Project` (`sub_project = Project(...); sub_project.cross_cutting.append(item); dumps_canonical(sub_project)`) which yields a different top-level shape. Plan acknowledges this ("Adjust the JSON shape if reviewers prefer..."). Make a call now rather than during implementation — leaving it open invites churn at review time. The bare-item shape matches the spec and is what a future `unarchive-cross` would parse most naturally.
