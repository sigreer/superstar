### docs/specs/2026-05-21-X17-transactional-spec-plan-artifacts-design.md

    1	# X17 — transactional spec and plan artifact handling
    2	
    3	**Status:** spec
    4	**Tasktool ID:** X17 (cross-cutting)
    5	**Date:** 2026-05-21
    6	
    7	## Problem
    8	
    9	The current Superstar workflow intentionally allows spec, plan, handoff, and reviewer-chain artifacts to be produced on the authoritative checkout (`main`). That is the right place for durable planning state: later agents need one canonical tasklist and one canonical set of workflow artifacts.
   10	
   11	The failure mode is that tasktool only owns `docs/tasklist.json`. A spec/planning agent can create or revise files under `docs/specs/`, `docs/plans/`, `docs/handoffs/`, `docs/reviewer/`, and `docs/archived-tasks/`, while separately updating `docs/tasklist.json` through `tasktool create`, `tasktool ref`, `tasktool archive-phase`, or manual edits. If those files are left unstaged or only partly staged, the next routed mutation fails with:
   12	
   13	> authoritative docs/tasklist.json has unstaged changes; commit, stash, or normalise them before running tasktool
   14	
   15	That guard is correct. It prevents a later `tasktool start` or `tasktool close` from writing over unattributed authoritative task state. But it catches the problem late, after the checkout has already accumulated loose workflow state.
   16	
   17	The recent X15/X16 collision is the concrete symptom: X15 spec/plan/tracker state was present in the authoritative checkout while another agent tried to run X16 lifecycle commands. Tasktool blocked the X16 mutation, but it did not provide a first-class way for the X15 planning agent to create, register, validate, stage, and optionally commit its workflow artifacts as one durable transaction.
   18	
   19	## Goals
   20	
   21	1. Add tasktool commands that make spec/plan/handoff/reviewer artifact registration transactional with the tasklist row they belong to.
   22	2. Make the safe path ergonomic enough that agents do not hand-edit `docs/tasklist.json` or leave orphan dated docs behind.
   23	3. Preserve the current model where planning artifacts live on the authoritative checkout and implementation still runs from isolated worktrees.
   24	4. Fail early when the authoritative checkout already has unsafe tasklist or artifact dirt.
   25	5. Update workflow skills so spec/plan agents use the new commands instead of treating artifact staging as an afterthought.
   26	
   27	## Non-goals
   28	
   29	- Generating spec or plan prose. Agents still write the documents; tasktool owns registration, validation, staging, and optional commit boundaries.
   30	- Replacing external-review. Reviewer-chain generation remains owned by the external-review tooling. Tasktool only registers and validates the chain artifact after it exists.
   31	- Auto-merging unrelated dirty state. The command refuses ambiguous checkouts rather than guessing what belongs to the current work item.
   32	- Moving planning off `main`. This spec keeps durable planning state on the authoritative checkout by design.
   33	- Changing implementation worktree creation or merge-back rules.
   34	
   35	## Design
   36	
   37	### 1. `tasktool artifact add`
   38	
   39	Add a new mutating command:
   40	
   41	```bash
   42	tasktool artifact add <id> --kind spec --path docs/specs/...
   43	tasktool artifact add <id> --kind plan --path docs/plans/...
   44	tasktool artifact add <id> --kind handoff --path docs/handoffs/...
   45	tasktool artifact add <id> --kind reviewer --path docs/reviewer/<chain-dir>/
   46	tasktool artifact add <id> --kind archive --path docs/archived-tasks/...
   47	```
   48	
   49	Semantics:
   50	
   51	- Routes through the configured authoritative checkout using the existing `_write_context` path.
   52	- Refuses if the authoritative `docs/tasklist.json` has unstaged changes, using the existing unsafe-dirty guard.
   53	- Resolves `<id>` through the same `_find_item` path used by `tasktool ref`, so short IDs behave consistently.
   54	- Requires `--path` to be repository-relative after normalization. Absolute paths are accepted only if they resolve inside the invocation repository; they are stored as relative paths.
   55	- Requires the target path to exist, except `--kind spec|plan|handoff --allow-missing` for the narrow case where the row is being reserved before the agent writes the file. The default is strict existence checking.
   56	- Adds the path to `item.refs` if not already present. For phase/slice-specific model fields that already exist, it also updates the typed field:
   57	  - `--kind spec` updates `spec_path` when the item has that field.
   58	  - `--kind plan` updates `plan_path` when the item has that field.
   59	  - `--kind reviewer` updates `reviewer_chain` for slices and `phase_reviewer_chain` for phases when applicable.
   60	  - Cross-cutting items continue to use `refs` only, because they intentionally have no typed spec/plan fields today.
   61	- Saves `docs/tasklist.json`, stages it, and stages the artifact path itself with `git add`.
   62	- Prints the registered relative path and whether it was newly added or already present.
   63	
   64	This command is the direct replacement for ad hoc `tasktool ref X --add <path>` during planning. `tasktool ref` remains available for generic references, but workflow skills should prefer `artifact add` for spec/plan/handoff/reviewer paths.
   65	
   66	### 2. `tasktool artifact status`
   67	
   68	Add a read-only diagnostic command:
   69	
   70	```bash
   71	tasktool artifact status [<id>] [--format text|json]
   72	```
   73	
   74	When `<id>` is omitted, it scans the active tasklist and the workflow artifact directories. It reports:
   75	
   76	- Referenced artifact paths that do not exist.
   77	- Existing dated spec/plan/handoff files that are not referenced by any tasklist row.
   78	- Reviewer-chain directories under `docs/reviewer/` that are not referenced by any row.
   79	- Workflow artifact files that are unstaged while `docs/tasklist.json` is staged or clean.
   80	- `docs/tasklist.json` changes that are unstaged while workflow artifacts are present.
   81	
   82	When `<id>` is supplied, the report is limited to that row and its references.
   83	
   84	This command does not mutate. It gives agents and hooks a cheap preflight for "will this planning state surprise the next tasktool mutation?"
   85	
   86	### 3. `tasktool artifact commit`
   87	
   88	Add an optional transaction closeout command:
   89	
   90	```bash
   91	tasktool artifact commit <id> --message "X17: add transactional artifact spec"
   92	```
   93	
   94	Semantics:
   95	
   96	- Routes to the authoritative checkout.
   97	- Refuses if `docs/tasklist.json` has unstaged changes before the transaction begins.
   98	- Runs `artifact status <id>` and refuses missing references or unreferenced dated artifacts for that ID's slug.
   99	- Stages `docs/tasklist.json` plus every referenced artifact path for the row.
  100	- Refuses if the staged diff contains paths outside:
  101	  - `docs/tasklist.json`
  102	  - `.tasktool/config.json`
  103	  - `docs/specs/`
  104	  - `docs/plans/`
  105	  - `docs/handoffs/`
  106	  - `docs/reviewer/`
  107	  - `docs/archived-tasks/`
  108	- Creates a git commit with the supplied message.
  109	- Does not push.
  110	
  111	This is deliberately separate from `artifact add`. Some agents may need multiple review iterations before committing. The important property is that tasktool can now close the planning transaction when the spec/plan/review bundle is ready.
  112	
  113	### 4. `tasktool prepare` as a convenience wrapper
  114	
  115	Add a higher-level command for the common "mint row and register artifacts" case:
  116	
  117	```bash
  118	tasktool prepare cross \
  119	  --title "Make spec and plan artifact handling transactional" \
  120	  --spec docs/specs/2026-05-21-X17-transactional-spec-plan-artifacts-design.md \
  121	  --plan docs/plans/2026-05-21-X17-transactional-spec-plan-artifacts.md \
  122	  --handoff docs/handoffs/2026-05-21-X17-transactional-spec-plan-artifacts-prompt.md
  123	```
  124	
  125	`prepare` is a composition of existing tasktool operations:
  126	
  127	1. Create the row (`create cross`, `create phase`, or `create slice`) if an ID was not supplied.
  128	2. Register the supplied artifact paths using `artifact add --allow-missing`.
  129	3. Stage `docs/tasklist.json`.
  130	4. Print the new ID and the exact files the agent must create next.
  131	
  132	`prepare` does not create empty spec/plan files by default. Empty docs look valid to filesystem checks while containing no useful contract. If a future workflow wants templates, that can be a separate flag with explicit template content.
  133	
  134	### 5. Skill updates
  135	
  136	Update these skills:
  137	
  138	- `skills/brainstorming/SKILL.md`: before writing a spec, create or prepare the tasktool row using `tasktool prepare` or `tasktool create` + `tasktool artifact add --kind spec --allow-missing`. After spec review passes, run `tasktool artifact add --kind reviewer` for the spec reviewer chain.
  139	- `skills/writing-plans/SKILL.md`: before writing the plan/handoff, register the intended paths with `tasktool artifact add --allow-missing`; after review passes, register the plan reviewer chain and run `tasktool artifact status <id>`.
  140	- `skills/tasklist-discipline/SKILL.md`: document that spec/plan/handoff/reviewer paths are workflow artifacts and should be registered through `tasktool artifact`, not generic refs or manual JSON edits.
  141	- `skills/external-review/SKILL.md`: after a successful spec/plan review, register the reviewer-chain directory with `tasktool artifact add --kind reviewer` when `docs/tasklist.json` exists.
  142	
  143	The skills should still commit according to the existing workflow. The new command gives them a deterministic staging and validation surface; it does not remove the need for commits.
  144	
  145	## Component boundaries
  146	
  147	- `tools/tasktool/artifacts.py` owns path classification, row-artifact mapping, orphan detection, and staging path calculation.
  148	- `tools/tasktool/commands.py` owns command orchestration and reuse of `_write_context`, `_find_item`, `_save`, and `_git_stage`.
  149	- `tools/tasktool/cli.py` owns argument parsing for `artifact` and `prepare`.
  150	- `tools/tasktool/tests/test_artifacts.py` covers pure path/status logic.
  151	- `tools/tasktool/tests/test_artifact_cli.py` covers command behavior through the CLI.
  152	
  153	Keeping path classification in a small module avoids growing `commands.py` into a mixed CLI, model, and filesystem-policy file.
  154	
  155	## Error handling
  156	
  157	- Unknown ID: reuse existing `cross-cutting X not found` / `phase not found` style errors from `_find_item`.
  158	- Path outside repository: `artifact path is outside repository: <path>`.
  159	- Missing path without `--allow-missing`: `artifact path does not exist: <path>`.
  160	- Unsupported path for kind: `spec artifacts must live under docs/specs/`, `plan artifacts must live under docs/plans/`, and equivalent messages for handoff/reviewer/archive.
  161	- Unsafe authoritative tasklist dirt: preserve the existing tasktool error.
  162	- `artifact commit` with unrelated staged files: print the disallowed paths and refuse.
  163	- `prepare` with both `--id` and a create-only shape that would allocate a new row: refuse with a usage error.
  164	
  165	## Testing
  166	
  167	Add focused pytest coverage:
  168	
  169	1. `artifact add` registers a spec path for an existing cross-cutting row, stages `docs/tasklist.json`, and stages the spec file.
  170	2. `artifact add --allow-missing` registers a future spec path and stages only `docs/tasklist.json`.
  171	3. `artifact add` rejects paths outside the repo.
  172	4. `artifact add --kind plan` rejects files outside `docs/plans/`.
  173	5. `artifact add --kind reviewer` accepts a directory under `docs/reviewer/` and registers it in `refs`.
  174	6. `artifact status` reports unreferenced dated spec/plan/handoff files.
  175	7. `artifact status <id>` reports missing referenced files for that row.
  176	8. `artifact status` exits non-zero when run with `--strict` and problems are present.
  177	9. `artifact commit <id>` stages only allowed workflow paths and creates a commit.
  178	10. `artifact commit <id>` refuses unrelated staged code changes.
  179	11. `prepare cross --title ... --spec ...` allocates the next X ID and registers intended artifact refs without creating empty files.
  180	12. `prepare --id X17 --spec ... --plan ...` registers artifacts against an existing row without allocating a new ID.
  181	13. Authority routing: running `artifact add` from a linked implementation worktree mutates and stages the authoritative checkout, not the worktree copy.
  182	14. Unsafe-dirty guard: `artifact add` refuses when authoritative `docs/tasklist.json` has unstaged bytes.
  183	
  184	Run gates:
  185	
  186	```bash
  187	PYTHONPATH=tools pytest tools/tasktool/tests -q
  188	tools/tasktool/tasktool validate --strict-format
  189	git diff --check
  190	```

  192	## Migration and rollout
  193	
  194	This is additive. Existing refs remain valid. No existing tasklist schema migration is required.
  195	
  196	After the command ships, planning agents should use this sequence:
  197	
  198	```bash
  199	tasktool prepare cross \
  200	  --title "<title>" \
  201	  --spec docs/specs/YYYY-MM-DD-XNN-slug-design.md
  202	
  203	# write spec, run review, then:
  204	tasktool artifact add XNN --kind reviewer --path docs/reviewer/<spec-chain>/
  205	tasktool artifact status XNN --strict
  206	git commit -m "XNN: add <slug> spec"
  207	
  208	# write plan + handoff, run plan review, then:
  209	tasktool artifact add XNN --kind plan --path docs/plans/YYYY-MM-DD-XNN-slug.md
  210	tasktool artifact add XNN --kind handoff --path docs/handoffs/YYYY-MM-DD-XNN-slug-prompt.md
  211	tasktool artifact add XNN --kind reviewer --path docs/reviewer/<plan-chain>/
  212	tasktool artifact status XNN --strict
  213	git commit -m "XNN: add <slug> plan"
  214	```
  215	
  216	Once skills adopt the sequence, loose spec/plan/reviewer artifacts on `main` become a visible status failure instead of hidden ambient state.
  217	
  218	## Open questions
  219	
  220	None. The design chooses explicit tasktool ownership of workflow artifact registration, while leaving prose generation and external-review behavior in their existing tools.
