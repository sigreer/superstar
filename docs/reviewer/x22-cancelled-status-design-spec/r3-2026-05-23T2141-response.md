1. Findings

F1. RESOLVED. Severity: blocking. The spec still requires both JSON-schema and semantic validation to reject `cancelled` tasks, including `_check_task()` and `validate_project()` tests (`docs/specs/2026-05-23-X22-cancelled-status-design.md:73-79`, `:223-226`, `:303-306`).

F2. RESOLVED. Severity: important. The schedule contract is concrete and grounded in the current row shape, preserving `depends_on`, narrowing `waiting_on`, and adding `cancelled_deps` in both JSON and text output (`docs/specs/2026-05-23-X22-cancelled-status-design.md:176-212`).

F3. RESOLVED. Severity: important. The spec now explicitly leaves global `phase-status` unchanged and scopes cancelled-dependency visibility to phase-scoped `schedule` (`docs/specs/2026-05-23-X22-cancelled-status-design.md:210-211`).

F4. RESOLVED. Severity: important. Active vs archived `show`/`brief` behavior is now explicit, including preserving the existing archived-X “not found in active tasklist” behavior (`docs/specs/2026-05-23-X22-cancelled-status-design.md:218-220`).

F5. RESOLVED. Severity: minor. The notification requirement is grounded in the existing generic `tasktool-status` notifier and no longer invents a status-specific audio cue (`docs/specs/2026-05-23-X22-cancelled-status-design.md:228-236`).

F6. RESOLVED. Severity: important. The prior archive-phase notification gap is fixed: the spec now requires cancelled phase archival to notify with the actual phase status and adds a regression test forbidding a misleading `done` event (`docs/specs/2026-05-23-X22-cancelled-status-design.md:238-241`).

F7. Severity: blocking. The task exclusion contract is still incomplete for cancelled parents. The spec says tasks remain unaffected and that cancelling a slice implicitly cancels open tasks “for the purposes of any caller that asks ‘is this row done?’” (`docs/specs/2026-05-23-X22-cancelled-status-design.md:21`, `:51`), and it says `list --open` excludes cancelled rows (`:218`). But current `cmd_list` walks tasks independently (`tools/tasktool/commands.py:1571-1577`) and filters only each item’s own status (`tools/tasktool/commands.py:1591-1604`). Since tasks cannot become `cancelled`, a cancelled slice or cascaded cancelled phase can still leak ready/in-progress child tasks into `tasktool list --open`. The spec needs an explicit rule and test for descendants of cancelled terminal parents, otherwise one of the named reports remains corrupted after cancellation.

2. Open questions / assumptions

- I assume tasks should not be status-mutated during slice cancellation; instead, open-list/reporting callers should suppress tasks whose parent slice is terminal. If that is wrong, the spec should say exactly how open child tasks are stamped or rendered.
- I also assume `tasktool cancel P1.S1.T1` must be rejected explicitly, because `close` currently accepts task IDs, while this feature’s allowed scopes exclude tasks.

3. Suggested document edits

- Add a `list --open`/descendant rule near Render and surfacing: when a slice is terminal, its child tasks are not emitted by open-row reports, even if their own task status is `ready` or `in_progress`.
- Add tests for `tasktool list --open` after cancelling a slice and after `cancel <phase> --cascade`, asserting no child tasks from cancelled slices appear.
- Add an explicit CLI rejection bullet and test for `tasktool cancel <task-id>`.
