    1	# X22 — Add `cancelled` terminal status to tasktool
    2	
    3	**Date:** 2026-05-23
    4	**ID:** X22 (cross-cutting)
    5	**Type:** Spec / design
    6	
    7	## Problem
    8	
    9	`tasktool` today models four statuses: `ready | in_progress | blocked | done`. There is no first-class way to record that a slice, cross-cutting item, or phase was **terminated without shipping** — scope dropped, deferred, superseded, or otherwise abandoned. Operators currently work around this by:
   10	
   11	- Marking the row `done` (lies about completion; passes through the post-slice review gate it shouldn't),
   12	- Leaving the row indefinitely in `ready` or `blocked` (clutters `--open` lists, distorts phase status), or
   13	- Hand-editing notes (loses the structured signal).
   14	
   15	Each workaround corrupts either the lifecycle audit trail, the post-slice/post-phase review gates, or the `list --open` / `phase-status` / `ready-slices` reports that downstream skills depend on.
   16	
   17	This spec defines a fifth status, `cancelled`, as a peer of `done` (terminal but explicitly *not* shipped), and the supporting CLI verb, schema split, gate behavior, dependency semantics, archive handling, and render rules.
   18	
   19	## Goals
   20	
   21	1. Add `cancelled` as a terminal status applicable to **slices**, **cross-cutting items**, and **phases** — not tasks.
   22	2. Provide a dedicated `tasktool cancel <id> --reason "<text>"` verb that is the only sanctioned path to enter the status.
   23	3. Preserve correctness of existing gating, scheduling, and archive logic by introducing a single `is_terminal(status)` helper and routing the "is this row open vs finished?" sites through it (without converting sites where the intent is specifically "shipped").
   24	4. Make dependency satisfaction strict: a `cancelled` dependency does **not** unblock downstream work.
   25	5. Keep the `closed` field's `YYYY-MM-DD` shape; record precise audit data in `notes`.
   26	
   27	## Non-goals
   28	
   29	- Un-cancelling a row through a dedicated verb. The emergency path (`TASKTOOL_RAW=1` + `validate --normalise`) is acceptable; cancellation is meant to be deliberate.
   30	- Adding a separate "cancellation report" artifact. The reason in `notes` is sufficient.
   31	- Changing the meaning of `blocked` (still runtime-blocked) or `depends_on` (still planning-time precondition).
   32	- Reverting prior decisions: tasks remain unaffected; their status enum stays `ready | in_progress | done`.
   33	
   34	## Decisions
   35	
   36	### Naming
   37	
   38	- The status value is the string literal `"cancelled"` (British/U.S.-agnostic in tasktool; matches `cancel` verb).
   39	- Enum constant: `Status.CANCELLED`.
   40	- Emoji: `🚫`.
   41	
   42	### Allowed scopes
   43	
   44	| Item type | Status set after this change |
   45	|-----------|------------------------------|
   46	| Task | `ready \| in_progress \| done` (unchanged) |
   47	| Slice | `ready \| in_progress \| blocked \| done \| cancelled` |
   48	| Cross-cutting | `ready \| in_progress \| done \| cancelled` |
   49	| Phase | `ready \| in_progress \| done \| cancelled` |
   50	
   51	Rationale for excluding tasks: in-slice tasks are intra-slice bookkeeping. They roll up with the parent slice; cancelling a slice implicitly cancels its open tasks for the purposes of any caller that asks "is this row done?".
   52	
   53	### Schema enums (`tools/tasktool/schema_gen.py`)
   54	
   55	Replace the existing pair:
   56	
   57	```python
   58	slice_status_enum = ["ready", "in_progress", "blocked", "done"]
   59	non_blocked_status_enum = ["ready", "in_progress", "done"]
   60	```
   61	
   62	with three explicit enums:
   63	
   64	```python
   65	task_status_enum  = ["ready", "in_progress", "done"]
   66	phase_status_enum = ["ready", "in_progress", "done", "cancelled"]
   67	cross_status_enum = ["ready", "in_progress", "done", "cancelled"]
   68	slice_status_enum = ["ready", "in_progress", "blocked", "done", "cancelled"]
   69	```
   70	
   71	Update each schema reference site (task, slice, phase, cross-cutting) to use its own enum. **Tasks must not parse `cancelled`** — the implementation plan must include a JSON-schema test asserting a task with `status="cancelled"` fails validation.
   72	
   73	### CLI verb
   74	
   75	```
   76	tasktool cancel <id> --reason "<text>" [--cascade] [--no-archive]
   77	```
   78	
   79	- `<id>` accepts the same forms as `close` (`P2`, `P2.S3`, `X22`).
   80	- `--reason` is required; empty string is rejected with a clear error.
   81	- `--cascade` is a phase-only flag (rejected for slice/X ids). When set on a phase, every slice in the phase whose status is **not** terminal (`done` or `cancelled`) is also cancelled, sharing the same reason text plus a suffix `(cascaded from <phase-id>)`.
   82	- `--no-archive` is an X-only flag (rejected for slice/phase ids). Suppresses the default auto-archive behavior on cross-cutting cancellation (mirrors `close <x-id> --no-archive`).
   83	- The verb stamps:
   84	  - `status = Status.CANCELLED`
   85	  - `closed = <today as YYYY-MM-DD>` (matches existing `_check_date` shape at `validate.py:62`)
   86	  - Appends to `notes`: `Cancelled <ISO-8601 timestamp>: <reason>` on its own line. For cascaded children, the suffix `(cascaded from <phase-id>)` is appended to the same line.
   87	- The verb refuses to run if the row is already terminal (`done` or `cancelled`), with a clear message.
   88	- The verb bypasses the external-review gate entirely. Cancelled work never shipped; reviewer verdict is meaningless. This is documented in the help text and the `tasklist-discipline` skill.
   89	
   90	### `set --status cancelled` rejection
   91	
   92	`tools/tasktool/cli.py:91` today restricts `set --status` choices to `["ready", "in_progress", "done"]`. The implementation **must not** add `cancelled` to that list. Additionally, `cmd_set` must explicitly raise with a helpful hint (`use \`tasktool cancel <id>\` to cancel`) if a future contributor widens the choices, providing defense in depth.
   93	
   94	### `tasktool close` interaction
   95	
   96	`tasktool close <id>` refuses if the row is already `cancelled` (distinct verb, distinct path; do not silently overwrite).
   97	
   98	### Phase cancellation: cascade rules
   99	
  100	- `tasktool cancel P2` (no `--cascade`) refuses when any slice in the phase is open (`ready`, `in_progress`, or `blocked`). The error message lists the open slice IDs.
  101	- `tasktool cancel P2 --cascade` cancels each open slice using the parent's reason plus `(cascaded from P2)`. Slices that are already `done` or already `cancelled` are **never touched**. The resulting phase legitimately shows mixed terminal children (e.g. `✅ S1, ✅ S2, 🚫 S3, 🚫 S4`).
  102	- The phase's own row transitions to `cancelled` only after the cascade succeeds.
  103	
  104	### `archive-phase` interaction
  105	
  106	`tasktool archive-phase <phase-id>` is updated:
  107	
  108	- Accepts a phase whose status is `done` **or** `cancelled`.
  109	- Accepts the phase only when every slice is terminal — `done` or `cancelled` (using the new `is_terminal` helper).
  110	- The post-phase external-review gate is skipped when the phase status is `cancelled`. The skip is recorded in the archive note (`Phase cancelled; post-phase review gate skipped`).
  111	- The archive markdown emitted by `archive-phase` records the phase's actual status (`done` or `cancelled`), not a coerced value.
  112	
  113	### Cross-cutting archive: `_archive_cross_at_root`
  114	
  115	- Loosen the precondition from `status == Status.DONE` to `is_terminal(status)`.
  116	- The archive markdown writer must read the row's actual status and emit `status: cancelled` in the archived stub when applicable. Today's writer hard-codes done semantics; this must be parameterized.
  117	- Default behavior on `tasktool cancel <x-id>` is to auto-archive (mirrors `tasktool close <x-id>`); `--no-archive` keeps the row visible in `cross_cutting` with status `cancelled`.
  118	
  119	### Terminal-vs-open helper
  120	
  121	Introduce a single helper:
  122	
  123	```python
  124	# tools/tasktool/model.py or a new tools/tasktool/lifecycle.py
  125	def is_terminal(status: Status) -> bool:
  126	    return status in (Status.DONE, Status.CANCELLED)
  127	```
  128	
  129	The implementation plan must audit every `Status.DONE` reference and decide per site whether to convert to `is_terminal()` or to keep strict `== DONE`. Initial mapping (subject to plan-time review):
  130	
  131	| Site | Current | Intended after change |
  132	|------|---------|------------------------|
  133	| `brief.py:78` (skip done tasks in render) | `is not Status.DONE` | `is not Status.DONE` — keep; tasks can't be cancelled |

  184	## Edge cases and risks
  185	
  186	- **Existing tasklists in the wild without `cancelled`**: schema is forward-compatible — old data has no `cancelled` rows and parses fine.   187	- **A row marked `cancelled` that also has `started=null`**: allowed. A slice can be cancelled before it ever started (deferred without beginning). Validation only requires `closed >= created`; `started` remains optional. Plan must add a test.
