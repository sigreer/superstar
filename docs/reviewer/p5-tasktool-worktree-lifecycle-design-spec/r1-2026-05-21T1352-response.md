1. Findings

F1 Severity: blocking — `tasktool close` is specified as the default pruning point, gated on “Branch is merged into the slice's authoritative parent,” but the current workflow closes slices before merge-back. The spec only updates `using-git-worktrees` and `tasklist-discipline` (`docs/specs/2026-05-21-P5-tasktool-worktree-lifecycle-design.md:136`, `:169`), while existing execution guidance says run `tasktool close <slice-id>` at slice boundary before phase close and before `finishing-a-development-branch` (`skills/executing-plans/SKILL.md:46`, `:53`, `:67`; `skills/finishing-a-development-branch/SKILL.md:121`). This is an implementation trap: either close must no longer require merged branches by default, or the spec must explicitly revise the slice/phase/merge-back workflow and acceptance gates.

F2 Severity: important — canonical name normalization is inconsistent. The layout says `.worktrees/worktree-<id>-<slug>` with `<id>` like `P5.S1`, while the JSON example uses `worktree-P5-S1-...`, and the historical convention cited is lowercase `worktree-p13-s2-...` (`docs/specs/2026-05-21-P5-tasktool-worktree-lifecycle-design.md:44`, `:45`, `:55`). Because branch name must equal directory basename (`:46`), implementers need one exact slugification rule for task IDs, case, dots, non-alphanumerics, and collision handling.

F3 Severity: important — worktree state after close/prune is under-specified. `--keep-worktree` says `worktree_path` is retained so `worktree list` can see it (`docs/specs/2026-05-21-P5-tasktool-worktree-lifecycle-design.md:99`), implying default prune may clear it, but the default behavior never says whether `worktree_path`, `worktree_branch`, or `worktree_in_place` are retained, nulled, or archived. The close-from-inside path explicitly skips removal after flipping lifecycle state (`:101`-`:106`), which can leave a “done” slice with a live recorded worktree unless the spec defines the post-close health and follow-up state.

F4 Severity: important — dispatched-subagent detection is not specific enough to implement the required tests. The spec names “harness-provided env var, parent-process fingerprint” only as examples (`docs/specs/2026-05-21-P5-tasktool-worktree-lifecycle-design.md:87`), but P5.S3 requires tests for “the subagent signal” (`:175`). Pick concrete supported signals, such as named env vars plus a test-only override, and define precedence/failure behavior.

F5 Severity: minor — legacy migration language contradicts itself. Non-goals says the installer “warns and migrates” `.claude/worktrees/` and `.codex/worktrees/` (`docs/specs/2026-05-21-P5-tasktool-worktree-lifecycle-design.md:37`), while installer design says no automatic migration and “warn” only (`:120`-`:122`). Use one behavior.

2. Open questions / assumptions

- Is P5 intentionally moving slice close to after merge-back, or should prune be a separate post-merge cleanup command while `tasktool close` keeps today’s review-gated lifecycle meaning?
- Should `tasktool worktree list` include closed/done rows indefinitely, only active rows, or active plus retained/dirty closed rows?
- Should `--ad-hoc` create an actual cross-cutting row, a separate ad-hoc store, or an untracked lifecycle record? “Not recorded in the open-work index” is not enough to drive storage and validation.
