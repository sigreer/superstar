### docs/specs/2026-06-02-P7-integration-surface-parallel-safety-design.md

    1	# P7 — Integration-surface-aware parallel slice safety
    2	
    3	**Status:** design (spec)
    4	**Date:** 2026-06-02
    5	**Phase ID:** `P7`
    6	
    7	## 1. Problem
    8	
    9	`tasktool` decides whether slices may run in parallel from **declared feature
   10	dependencies** (`Slice.depends_on`) and the `parallel_group` tag. Those answer
   11	"does S4's feature need S3's feature first?" They do **not** answer the question
   12	that actually governs safe parallel execution: **what shared write surface does
   13	each slice mutate?**
   14	
   15	This gap produced a real failure in the `multistore` project, phase P20. Four
   16	storefront-marketing slices (`P20.S2`–`P20.S5`) each declared a dependency only
   17	on the bootstrap slice `P20.S1`, so `tasktool ready-slices`/`schedule` reported
   18	them as independently executable. They were feature-distinct (slider, promo
   19	bands, overlays, blog) but **integration-overlapping**: every one of them wrote
   20	the same centralized CMS-block machinery — block contracts, parser allowlists,
   21	Directus schema/seed files, renderer dispatch, theme CSS tails, and the homepage
   22	ordering array.
   23	
   24	The observed consequences:
   25	
   26	1. **Conflict-bomb merges.** `P20.S4`'s merge conflicted across `page-renderer.tsx`,
   27	   theme CSS, reviewer-request artifacts, `docs/tasklist.json`, Directus
   28	   bootstrap/schema/seed files, content-contract schemas/types, and parser tests.
   29	2. **Stale-base merges.** `P20.S4` was completed in a worktree that branched from
   30	   `main` *before* `P20.S2`/`P20.S3` and their cleanup landed. The worktree
   31	   snapshot was older than `main`, so the merge replayed churn that was already
   32	   integrated.
   33	3. **A real semantic collision, not just textual churn.** `P20.S3` and `P20.S4`
   34	   independently chose homepage sort slot `15`. Nothing forced the second slice
   35	   onto a free slot at planning time; the collision was discovered and resolved
   36	   at merge.
   37	4. **Merge-unsafe reviewer artifacts.** Generated reviewer-request files
   38	   add/add-conflicted despite not being behavioral code.
   39	
   40	The root cause is **dependency modeling by feature intent rather than by
   41	integration surface.** "Slider" and "promo bands" were non-dependent product
   42	slices, but they both wrote the same registry, schema, seed arrays, ordering
   43	slots, parser unions, and theme areas. The tool allowed parallel execution
   44	because the declared dependencies were technically satisfied.
   45	
   46	## 2. Goals
   47	
   48	1. **Prevention.** Let planning declare, per slice, the **integration surfaces**
   49	   it writes and the **scarce resources** it allocates. `tasktool` warns when
   50	   sibling ready/in-progress slices share a surface with no dependency or
   51	   coordination link, and *refuses* a duplicate scarce-resource allocation.
   52	2. **Recovery.** When a sibling slice has landed on the base branch since a
   53	   slice's worktree branched, surface that fact reliably and provide a
   54	   conservative "integrate current main" path before the post-slice review/merge,
   55	   plus a documented centralized-registry merge playbook.
   56	3. **Merge-safe reviewer artifacts.** Generated reviewer-request files must never
   57	   add/add-conflict between sibling worktrees.
   58	4. **Plan ↔ tracker coherence.** Declared surfaces/reservations must be reflected
   59	   in planning artifacts so the plan and the tracker cannot silently diverge.
   60	
   61	## 3. Non-goals (explicit)
   62	
   63	- **Directus-specific verifier diagnostics and stale-token handling.** These were
   64	  real `multistore` pain points (a stale `DIRECTUS_ADMIN_TOKEN` shadowing valid
   65	  admin credentials made a non-code problem look like a schema failure), but they
   66	  are project-specific. Superstar core is general-purpose and zero-dependency;
   67	  Directus tooling belongs in the `multistore` project, not here.
   68	- **Automatic merge-conflict resolution.** The tooling detects and routes; it does
   69	  not auto-merge semantic conflicts.
   70	- **Path-glob surface *inference* as the primary model.** Explicit declaration is
   71	  the source of truth. A path-glob comparison survives only as a deferred,
   72	  warning-only post-implementation *audit* (§4.G), never as the planning model.
   73	- **A "touches existing resource" reservation kind.** Reservations model scarce
   74	  *allocations* (claiming a new value). Modifying a shared existing resource is a
   75	  *surface/coordination* concern, not an allocation, so maintenance work is not
   76	  falsely blocked. A future "touches-existing" field is noted, not built here.
   77	- **`worktree sync` as an unconditional command.** Detection ships first; the
   78	  mutating sync command is gated behind strict preconditions and is the explicit
   79	  deferral candidate if scope tightens.
   80	
   81	## 4. Design
   82	
   83	### 4.A Data model (`model.py`, schema `v2 → v3`; `migrate.py`)
   84	
   85	Add to `Slice`:
   86	
   87	- `integration_surfaces: list[str]` — conventional surface tags naming shared
   88	  write areas the slice mutates. Free-form strings, but a recommended vocabulary
   89	  is documented in `tasklist-discipline` (e.g. `cms-block-registry`,
   90	  `directus-schema`, `page-renderer-dispatch`, `theme-tail-css`,
   91	  `content-contract-types`, `reviewer-artifacts`). Default `[]`.
   92	- `reservations: list[Reservation]` where
   93	  `Reservation = {resource: str, value: str, scope: "phase" | "project", note: str | None}`.
   94	  A reservation is a **scarce allocation claim** on a single value
   95	  (`homepage-sort:15`, `directus-collection:homepage_slider`, `route-slug:/offers`,
   96	  `block-kind:slider`, `cache-tag:home`). Default `[]`.
   97	- `coordination_group: str | None` — names a set of slices that *intentionally*
   98	  share an integration surface and agree to coordinate (serialize reviews,
   99	  designate an integration owner, run the registry merge playbook). Distinct from
  100	  `parallel_group`, which asserts independent parallelism. Default `None`.
  101	- `worktree_base_sha: str | None` — the base-branch commit the slice's worktree
  102	  was created from, recorded at `tasktool start`. Enables reliable
  103	  "a sibling landed since this slice branched" detection that survives later
  104	  rebases/merges, instead of fragile merge-base inference. Default `None`.
  105	
  106	Add to `Project`:
  107	
  108	- `reservations_ledger: list[Reservation]` — project-scoped reservations copied
  109	  here when their owning phase is archived, so project-scope uniqueness checks
  110	  survive removal of shipped phases from the active tracker. Default `[]`.
  111	
  112	Schema bump to `v3`. Migration is additive: missing fields default to empty/`None`
  113	and `reservations_ledger` to `[]`. Round-trip and v1/v2 compatibility tests
  114	extended.
  115	
  116	### 4.B Declaration CLI (`cli.py` + `commands.py`)
  117	
  118	```sh
  119	tasktool surface add <slice-id> <surface> [<surface>...]
  120	tasktool surface remove <slice-id> <surface>
  121	tasktool surface list [<phase-id>]
  122	
  123	tasktool reserve add <slice-id> <resource>:<value> [--scope phase|project] [--note "..."]
  124	tasktool reserve remove <slice-id> <resource>:<value>
  125	tasktool reserve list [<phase-id>]
  126	
  127	tasktool coordinate <slice-id> --group <name>     # set coordination_group
  128	tasktool coordinate <slice-id> --clear
  129	```
  130	
  131	- `surface`/`coordinate` are declaration-only; they never refuse.
  132	- **`reserve add` refuses** when the same `resource:value` is already held by
  133	  another **non-cancelled** slice within the relevant scope:
  134	  - `scope: phase` — checks other non-cancelled slices in the same phase. Done
  135	    slices count: a done slice shipped that value to `main`, so the slot is taken.
  136	  - `scope: project` — checks all non-cancelled slices across **active** phases
  137	    *and* `Project.reservations_ledger`.
  138	  The refusal names the holding slice and value. `--force` overrides and records
  139	  a timestamped note on both the reserving slice and (for audit) the override
  140	  reason. This refusal is the gate that would have forced `P20.S4` off slot `15`
  141	  at planning time.
  142	- On `tasktool archive-phase`, project-scoped reservations from the phase's
  143	  non-cancelled slices are appended to `Project.reservations_ledger` (deduped).
  144	
  145	### 4.C Scheduling overlap detection (`commands.py`)
  146	
  147	Augment the existing scheduling reporters; **surface overlap is a warning, not a
  148	block** (surfaces are coarse — two slices may touch the same registry in
  149	non-conflicting ways), while **reservation contention is already prevented at
  150	declaration time**.
  151	
  152	- `cmd_ready_slices` and `cmd_schedule`: for each ready/in-progress slice, compute
  153	  the set of other non-terminal slices that (a) share ≥1 integration surface,
  154	  (b) have **no** `depends_on` link in either direction, and (c) are **not** in
  155	  the same `coordination_group`. Emit a `surface_overlap` field/warning listing
  156	  the sibling(s) and shared surface(s). Slices in a shared `coordination_group`
  157	  are reported as `coordinated`, not warned.
  158	- New `tasktool surface check <phase-id>` — a dedicated read-only report:
  159	  - every unguarded surface overlap (siblings sharing a surface without a dep or
  160	    coordination link),
  161	  - every coordinated surface (shared surface within a `coordination_group`),
  162	  - reservation contention within the phase (should be empty if `reserve add`
  163	    refusal held; surfaced for audit and for `--force` overrides).
  164	  Text and `--format json`. Intended to be run during ratification and before
  165	  parallel dispatch.
  166	- `cmd_ratify --parallel-group <g>`: when adding a slice whose surfaces overlap
  167	  another slice already in that `parallel_group` with no dep/coordination link,
  168	  print a warning (does not refuse). Steers the planner toward either a
  169	  `depends_on` (serialize) or a `coordination_group` (coordinate).
  170	
  171	### 4.D Worktree integration detection (`worktree*.py`, `commands.py`)
  172	
  173	- `tasktool start` records `worktree_base_sha` = the base-branch HEAD the worktree
  174	  branched from (the commit `git worktree add -b` forked from). For `--in-place`
  175	  and `--adopt`, record the current base-branch HEAD / the adopted branch's
  176	  merge-base with base, respectively.
  177	- Extend `tasktool worktree status` with an `--integration` mode that reports, for
  178	  a slice:
  179	  - commits the base branch is ahead of `worktree_base_sha`,
  180	  - which **sibling slices** (same phase) closed/landed on base since
  181	    `worktree_base_sha`,
  182	  - whether any landed sibling shares an integration surface with this slice
  183	    (i.e. "you are stale against a sibling that wrote a surface you also write").
  184	  Detection/reporting only — hard to misuse, immediate value.
  185	
  186	### 4.E Conservative `worktree sync` (`worktree*.py`) — deferral candidate
  187	
  188	`tasktool worktree sync <slice-id>` integrates the current base branch into the
  189	slice's worktree branch, with strict preconditions, so the recovery checkpoint
  190	has a first-class command instead of raw git:
  191	
  192	- refuses unless the worktree tree is clean,
  193	- requires the configured authoritative base branch (no guessing),
  194	- requires an explicit `--merge` or `--rebase` choice (no default mutation),
  195	- refuses if there is unresolved tasklist drift,
  196	- on success, prints the follow-up (regenerate derived artifacts, rerun
  197	  verification) rather than assuming it.
  198	
  199	Ships **after** §4.D. If scope tightens, `sync` is deferred and the recovery
  200	checkpoint (§4.F) falls back to documented raw-git steps; detection (§4.D) still
  201	delivers the core value.
  202	
  203	### 4.F Skill changes (recovery + discipline)
  204	
  205	- **`subagent-driven-development`:**
  206	  1. After `tasktool ready-slices <phase-id>`, run `tasktool surface check
  207	     <phase-id>`. Do **not** parallel-dispatch slices that share an integration
  208	     surface without a declared `depends_on` or a shared `coordination_group` —
  209	     serialize them (add a dep) or coordinate them (assign a `coordination_group`,
  210	     designate an integration owner, plan to run the registry playbook).
  211	  2. New **"integrate current main" checkpoint** in the slice-end sequence,
  212	     *before* `external-review --kind post-slice`: run `tasktool worktree status
  213	     <slice-id> --integration`. If a sibling has landed since `worktree_base_sha`,
  214	     integrate base (`tasktool worktree sync … --merge|--rebase`, or documented
  215	     raw-git fallback), regenerate derived artifacts (checksums/snapshots), rerun
  216	     verification, **then** run the post-slice review.
  217	  3. Reference a new **centralized-registry merge playbook**
  218	     (`skills/subagent-driven-development/references/registry-merge-playbook.md`):
  219	     preserve **both** semantic additions, regenerate checksums/snapshots, rerun
  220	     focused parser/schema/seed tests, then rerun integrated verification.
  221	- **`tasklist-discipline`:** document `surface`/`reserve`/`coordinate` in the
  222	  conceptual model and daily-commands list; document the recommended surface
  223	  vocabulary and the `coordination_group` vs `parallel_group` distinction; add
  224	  red-flag rows:
  225	  - "These slices are feature-independent, so they're parallel-safe" → parallel
  226	    safety is about **write surface**, not feature independence; declare surfaces
  227	    and run `surface check`.
  228	  - "I'll pick a sort slot / collection name / route slug freely" → **reserve** it
  229	    so siblings cannot collide; for project-global resources use `--scope project`.
  230	  - "We both need the CMS registry, so I'll just `parallel_group` them" → shared
  231	    surface needs a `coordination_group` (coordinate) or a `depends_on`
  232	    (serialize), not a `parallel_group` (which asserts independence).
  233	- **`phase-planning` / `writing-plans`:** when proposing parallel groups, declare
  234	  each slice's integration surfaces and reservations and emit a **surface/
  235	  reservation table** in the plan; run `tasktool surface check <phase-id>` before
  236	  ratifying parallel groups.
  237	
  238	### 4.G Plan ↔ tracker drift enforcement (`validate.py`, skills) — partial defer OK
  239	
  240	- Plans (and phase-planning docs) include a structured **surface/reservation
  241	  table** per slice (enforced by the skills in §4.F).
  242	- `tasktool validate` (or `artifact status --strict`) gains a check that declared
  243	  `integration_surfaces`/`reservations` on a slice are reflected in its plan's
  244	  table, flagging drift. Where parsing the plan table is too brittle for this
  245	  phase, the minimum bar is a `validate` warning when a slice in a `parallel_group`
  246	  declares **no** surfaces at all (the "you forgot to think about this" nudge).
  247	
  248	### 4.H Merge-safe reviewer artifacts (`external-review`)
  249	
  250	Generated reviewer-request files must be slice-scoped so two sibling worktrees
  251	never write the same path. The exact current naming is confirmed during planning
  252	(reviewer chains are already per-slice folders; the conflict came from a shared or
  253	phase-level request path). Fix by guaranteeing per-slice/round-unique request
  254	paths and, where a shared file is unavoidable, an append/merge-safe format.
  255	
  256	### 4.I Deferred / future (recorded, not built)
  257	
  258	- `tasktool surface audit <slice-id>` — compares the slice branch diff to
  259	  configurable path globs and warns on **undeclared** surfaces ("you touched
  260	  `infra/directus/**` but did not declare `directus-schema`"). Warning-only safety
  261	  net; complements but does not replace explicit declaration.
  262	- A `reservation.touches_existing` distinction for maintenance edits to shared
  263	  resources.
  264	- Cross-project (multi-repo) reservation registries.
