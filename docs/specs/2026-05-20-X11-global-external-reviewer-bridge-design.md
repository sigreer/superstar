# X11 - Make external-reviewer a global bridge command

- **Status:** spec
- **Tasktool ID:** X11 (cross-cutting)
- **Date:** 2026-05-20
- **Owner:** Simon Greer
- **Touches:** `skills/external-review/SKILL.md`, `skills/project-setup/SKILL.md`, `skills/tasklist-discipline/SKILL.md`, `skills/external-review/tests/`, `skills/project-setup/scripts/`, `tests/claude-code/`, `docs/handoffs/`

## Problem

Superstar currently treats the external-review bridge as a project-vendored script. Consuming repos are instructed to run:

```bash
python3 scripts/external-reviewer.py review ...
```

That duplicates the bridge/parser/state-machine code into each project. When the source bridge changes in this repo, existing project copies can silently drift.

The recent Multistore failure showed the operational cost. In `/home/simon/Dev/sigreer/multistore`, the chain `docs/reviewer/p13-s4-remove-8bit-variant-P13-S4-post-slice/` contained Claude-style bare bold verdict lines:

- `r1-2026-05-20T1205-primary-response.md`: `**Verdict: revise**`
- `r2-2026-05-20T1214-response.md`: `**Verdict: ready**`

But `chain.json` persisted `verdict: null` and `verdict_valid: false` because Multistore was running its stale repo-local `scripts/external-reviewer.py`, not the current source bridge in Superstar.

The runtime paths are different for each tool:

- `tasktool` is already global. `/home/simon/.local/bin/tasktool` sets `PYTHONPATH=/home/simon/Dev/sigreer/skills/superstar/tools` and runs `python3 -m tasktool`, so tasktool fixes are immediately picked up after updating Superstar.
- `reviewer-agent` is already global and is only the provider subprocess. The P13.S4 response headers confirm `Reviewer command: reviewer-agent` and `Reviewer provider: claude`.
- `scripts/external-reviewer.py` is the stale duplicated component. It parses reviewer responses and writes `chain.json`.
- `/home/simon/.local/bin/reviewer` is not a safe canonical command because, in Multistore, it can conditionally dispatch to legacy `scripts/third-party-review.py`.

The failing path was:

```text
agent in Multistore
-> python3 scripts/external-reviewer.py review ...
   # repo-local stale bridge/parser
-> /home/simon/.local/bin/reviewer-agent
-> claude --print ...
```

## Goals

- Make `external-reviewer` the global canonical review-chain bridge command.
- Stop copying full `scripts/external-reviewer.py` bridge implementations into projects.
- Preserve the current `docs/reviewer/...` chain storage format and gate behavior.
- Keep `reviewer-agent` as the global provider runner used by the bridge.
- Keep `tasktool` behavior global and unchanged.
- Make stale repo-local `scripts/external-reviewer.py` copies visible as legacy drift during project setup/audit.
- Provide a backwards-compatible transition path for old handoffs that still invoke `python3 scripts/external-reviewer.py`.

## Non-goals

- Rework verdict parsing. X10 owns the Claude bare-verdict parser fix.
- Change `chain.json` schema, reviewer chain folder names, or tasktool reviewer-gate logic.
- Replace or route through `/home/simon/.local/bin/reviewer`.
- Change `reviewer-agent` provider selection, sandboxing, prompt transport, or rate-limit behavior.
- Install third-party dependencies.
- Automatically edit arbitrary downstream repos from this Superstar change.

## Command Model

The canonical runtime model is:

```text
tasktool          global task tracker CLI
external-reviewer global Superstar review-chain bridge
reviewer-agent    global provider subprocess used by external-reviewer
```

The canonical review invocation becomes:

```bash
external-reviewer review \
  --kind <spec|plan|post-slice|post-phase> \
  --file <path> \
  --work-id <id> \
  --emit json
```

`--work-id` is required for `post-slice` and `post-phase` reviews. It is optional for `spec` and `plan` reviews, but recommended when a tasktool ID already exists so the chain folder and metadata stay tied to the tracked work.

`external-reviewer` owns:

- prompt construction;
- provider command invocation;
- verdict parsing;
- `docs/reviewer/...` request/response artifacts;
- `chain.json` updates;
- rate-limit/manual-approve/human-bridge subcommands.

`reviewer-agent` owns:

- launching the selected provider CLI;
- honoring the sandbox/output environment supplied by the bridge;
- returning provider output to the bridge.

The command `/home/simon/.local/bin/reviewer` is explicitly non-canonical. It may remain for local legacy workflows, but Superstar skills and setup output must not recommend it.

## Design

### 1. Add a global `external-reviewer` installer

Add an installer analogous to `tools/tasktool/install.sh`. The preferred location is:

```text
skills/external-review/install.sh
```

The installer writes:

```text
~/.local/bin/external-reviewer
```

with executable content equivalent to:

```bash
#!/usr/bin/env bash
# external-reviewer shim - generated by Superstar
exec python3 "<absolute path resolved from the installer>/scripts/external-reviewer.py" "$@"
```

The installer must self-locate like `tools/tasktool/install.sh:29-30`: compute `SCRIPT_DIR` from `${BASH_SOURCE[0]}`, then resolve the sibling source script as `$SCRIPT_DIR/scripts/external-reviewer.py`. The generated shim embeds the absolute path resolved at install time, rewriting any `$HOME/` prefix to a literal `$HOME/` token so the shim expands it at runtime instead of pinning Simon's home directory into the file. It must not contain a hardcoded `/home/simon/...` string.

This local fork should point at the source checkout by default, matching the current global `tasktool` semantics on Simon's machine. `tools/tasktool/install.sh:50-54` writes a shim that exports `PYTHONPATH="${PKG_ROOT}..."` where `PKG_ROOT` is resolved from the installer's own location, so fixing `tools/tasktool/...` in the source checkout immediately fixes future global `tasktool` invocations. The `external-reviewer` installer should mirror that source-tree update model for `skills/external-review/scripts/external-reviewer.py`.

Release semantics remain simple:

- The local-source shim is the default for this private fork.
- Plugin-cache shims are not required for this change.
- If a future release wants cache-pinned behavior, it can add an explicit `--target plugin-cache` mode. That is out of scope here because current `tasktool` already points at the source tree.

Installer behavior should match `tasktool`'s guardrails:

- Create `~/.local/bin` if needed.
- Support `EXTERNAL_REVIEWER_BIN=<dir>` so tests and CI can install into a temporary bin directory without mutating the user's real `~/.local/bin`. If unset, default to `~/.local/bin`.
- Refuse to overwrite a non-Superstar `external-reviewer` unless `--force` is passed.
- Treat an existing generated shim as updatable.
- Run `external-reviewer --help` as a self-test before reporting success.
- Print a diagnostic equivalent to `Pointing at <source external-reviewer.py>` so operators can see which source checkout the shim follows.

### 3. Update `project-setup` audit and scaffold behavior

`skills/project-setup/SKILL.md` should stop requiring a full repo-local bridge script.

Replace the current row:

```text
scripts/external-reviewer.py present at repo root, or AGENT_REVIEWER_CMD is set
```

with two distinct checks:

1. **Global external-reviewer bridge available**
   - Pass: `command -v external-reviewer` succeeds and `external-reviewer --help` exits 0.
   - Missing: offer to run or print `bash /home/simon/Dev/sigreer/skills/superstar/skills/external-review/install.sh` in this fork, or the equivalent path to the active Superstar checkout in another install.
   - Scaffold action: install the global shim only after user confirmation.

2. **Repo-local legacy bridge drift**
   - Pass: no `scripts/external-reviewer.py` exists.
   - Compatibility-pass: `scripts/external-reviewer.py` exists and matches the documented compatibility shim marker: it contains `Compatibility shim for old Superstar handoffs` and delegates to `external-reviewer`.
   - Partial: `scripts/external-reviewer.py` exists but does not match the documented compatibility shim marker. Treat every other local file as legacy drift; do not try to distinguish full vendored copies from unknown scripts.
   - Scaffold action for partial: offer to replace the file with the compatibility shim, not to copy source bridge code.

The setup boundary classification should treat full repo-local `scripts/external-reviewer.py` as legacy drift. A generated compatibility shim is setup/migration artifact when newly created, but it is not considered parser drift after committed.

`project-setup` should continue to audit `reviewer-agent` separately:

- Pass: `AGENT_REVIEWER_CMD` is set, or `reviewer-agent` is on `PATH`.
- Scaffold action: print or install the existing `skills/project-setup/scripts/reviewer-agent` wrapper after confirmation.

### 4. Compatibility shim for existing repos

Existing repos may contain old handoffs, plans, or muscle memory that still run:

```bash
python3 scripts/external-reviewer.py review ...
```

The migration path is to replace full repo-local bridge copies with a tiny compatibility shim. The shim should contain no parser, prompt, state, or provider logic. It should exec the global command:

```python
#!/usr/bin/env python3
"""Compatibility shim for old Superstar handoffs.

The canonical bridge is the global `external-reviewer` command.
"""

from __future__ import annotations

import os
import shutil
import sys


def main() -> int:
    target = shutil.which("external-reviewer")
    if target is None:
        print(
            "scripts/external-reviewer.py is a compatibility shim, but "
            "`external-reviewer` is not on PATH. Install it with Superstar's "
            "skills/external-review/install.sh.",
            file=sys.stderr,
        )
        return 127
    script_path = os.path.realpath(__file__)
    target_path = os.path.realpath(target)
    if target_path == script_path:
        print(
            "scripts/external-reviewer.py resolved `external-reviewer` back to "
            "itself. Fix PATH so the global Superstar bridge appears before "
            "this repo-local compatibility shim.",
            file=sys.stderr,
        )
        return 127
    os.execvp(target, [target, *sys.argv[1:]])
    return 127


if __name__ == "__main__":
    raise SystemExit(main())
```

This compatibility mode is deliberately transitional:

- New Superstar-generated guidance must never prefer it.
- Project setup may offer it for existing repos so stale parser drift is removed without breaking old commands.
- The audit should distinguish this shim from a full vendored bridge by looking for a stable marker string such as `Compatibility shim for old Superstar handoffs` and an `external-reviewer` exec path.

## Migration and Backwards Compatibility

Recommended downstream migration for a repo such as Multistore:

1. Update Superstar source.
2. Install the global bridge:
   ```bash
   bash /home/simon/Dev/sigreer/skills/superstar/skills/external-review/install.sh
   external-reviewer --help
   ```
3. Run project setup/audit in the downstream repo.
4. If `scripts/external-reviewer.py` is a full vendored bridge, replace it with the compatibility shim.
5. Keep existing `docs/reviewer/...` chain folders untouched.
6. Use `external-reviewer review ...` for all new review rounds.

This preserves old handoffs while preventing stale bridge code from shadowing the current parser/state machine.

## Alternatives Considered

### A. Hard remove repo-local `scripts/external-reviewer.py`

This is the cleanest end state, but it breaks old handoffs and plans immediately. The failure mode would shift from silent stale parser drift to command-not-found interruptions. That is acceptable later, but too abrupt for the current installed base.

### B. Keep vendoring and add drift detection

This would compare versions or checksums between the source bridge and project copies. It reduces surprise but keeps the duplicated runtime code and makes every downstream repo responsible for staying synced. It does not match the already-successful `tasktool` global model.

### C. Make `/home/simon/.local/bin/reviewer` canonical

Rejected. In Multistore, `reviewer` can dispatch to legacy `scripts/third-party-review.py` when present. That makes it ambiguous as a workflow contract. `external-reviewer` must be the bridge; `reviewer-agent` must remain the provider runner.

- Unit test or shell test that a generated `scripts/external-reviewer.py` shim invokes a fake `external-reviewer` earlier on `PATH` with the original arguments.

  - no local file -> pass;

## Acceptance Criteria

- New Superstar sessions instruct agents to run `external-reviewer`, not `python3 scripts/external-reviewer.py`.
- `external-reviewer --help` works from any repo, including Multistore, after running the installer.
- A stale repo-local `scripts/external-reviewer.py` can no longer silently shadow the current bridge in recommended workflows.
- `project-setup` guidance and static wording tests report any non-shim repo-local `scripts/external-reviewer.py` as legacy drift, not success. No setup audit CLI is implemented in this spec.
- Existing review chain storage remains unchanged under `docs/reviewer/...`.
- `reviewer-agent` remains the provider runner and still receives the `AGENT_REVIEWER_*` environment variables from the bridge.
- `tasktool` behavior remains global and unchanged.
- Tests cover the command/path contract and the stale-copy/drift case.
- `/home/simon/.local/bin/reviewer` is not documented as canonical.

## Risks and Rollback

- **Risk:** Old plans continue to run `python3 scripts/external-reviewer.py`. Mitigation: compatibility shim preserves that command while delegating to the global bridge.
- **Risk:** A non-generated user script exists at `~/.local/bin/external-reviewer`. Mitigation: installer refuses to overwrite without `--force`.
- **Risk:** Agents keep using stale examples from historical docs. Mitigation: update live skills and static wording tests; do not rely on historical plan cleanup.
- **Risk:** Source-tree shim semantics are surprising for released plugin users. Mitigation: this private fork already uses source-tree semantics for `tasktool`; document that explicitly. Add plugin-cache mode later only if release behavior needs it.
- **Rollback:** Restore previous skill guidance and remove the global shim. Downstream compatibility shims would then fail clearly with exit 127 instead of silently running stale parser code.

## Out of Scope Follow-ups

- Remove compatibility shims entirely after old handoffs age out.
- Add a `project-setup --apply` script-level implementation for automated drift replacement if the skill eventually grows a real setup CLI.
- Add plugin-cache-pinned `external-reviewer` installation mode if local release semantics diverge from source-tree development.
