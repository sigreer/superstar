# P9.S2 — Deterministic preflight gate + strengthened self-review checklists

**Date:** 2026-06-09
**Status:** draft
**Tracker:** P9.S2 (slice of P9 — Review-pipeline efficiency)
**Parent spec:** `docs/specs/2026-06-06-P9-review-pipeline-efficiency-design.md` (S2 section)
**Depends on:** P9.S1 (done)

## Problem

P9.S1 made each reviewer round cheaper (kind-aware depth defaults, model
tiering) and added a rounds-per-slice metric. It did not reduce *round count*.
The phase baseline (multistore, `external-reviewer stats`, 2026-06-06) shows
spec/plan/post-slice chains averaging ~2.3–2.7 rounds each, with revise rates of
34–47%. The phase design observes that many `revise` findings are mechanical —
placeholder text, dangling file references, missing acceptance/verification
sections, oversized tracker context — and are catchable locally for free before
the first paid reviewer round.

Today nothing catches these locally. An author writes a spec or plan, invokes
`external-reviewer review`, and pays a full reviewer round to be told "this
references a file that does not exist" or "no verification section." That round
plus its fix cycle is pure avoidable cost.

## Goal

Catch mechanical revise-class findings deterministically (no LLM calls) before
the first paid reviewer round, and prime authors to self-check the
non-mechanical drivers. Concretely:

- A `external-reviewer preflight` subcommand that runs deterministic checks and
  reports findings.
- `external-reviewer review` auto-runs those checks on round 1 and refuses on
  failure (escape hatch `--no-preflight`).
- `brainstorming` and `writing-plans` self-review checklists name the top
  historical revise drivers and instruct running preflight before external
  review.

This is S2 of the phase. It does not change the verdict contract, chain layout,
provider invocation, or any S1 behaviour.

## Non-goals / out of scope

- No LLM calls in preflight — every check is deterministic and offline.
- No new review *kinds*, no verdict-contract or chain-folder changes.
- No combined spec+plan gate (that is S3; `--combined-gate`).
- No changes to S1 behaviour (depth defaults, model tiering, resolution gate,
  stats). S2 only adds the preflight surface and the checklist text.
- No consumer-repo (multistore) changes.

## Design

All CLI behaviour lives in
`skills/external-review/scripts/external-reviewer.py`. Documentation lives in
`skills/external-review/SKILL.md`, `skills/brainstorming/SKILL.md`, and
`skills/writing-plans/SKILL.md`. Tests live in
`skills/external-review/tests/`.

### S2.a — `external-reviewer preflight` subcommand

```
external-reviewer preflight --kind <kind> --file <target> [--context <path>]... [--emit json]
```

`--kind` takes the same choices as `review`
(`spec|plan|design|implementation|post-slice|post-phase|other`). `--file` is the
target document; `--context` may repeat. `--emit` is `text` (default) or `json`.

A single pure function does the work so the subcommand and the round-1
auto-gate share one implementation:

```
run_preflight_checks(kind, target: Path, context: list[Path], repo_root: Path) -> PreflightResult
```

`PreflightResult` carries an ordered list of findings, each a small record:
`check` (which check produced it), `severity` (`failure` | `warning`),
`message`, and optional `line` / `path`. Two helpers expose the rollup:
`PreflightResult.failures` and `.warnings`. The function performs **no I/O on
the chain folder and no LLM calls** — it only reads the target and context
files from disk.

The deterministic checks:

**1. Target readable.** The target exists, is non-empty after stripping
whitespace, and decodes as UTF-8. Any failure here is a `failure` and short-
circuits the remaining content checks (a binary or empty target cannot be
meaningfully scanned).

**2. Placeholder scan.** The whole-token placeholders `TBD`, `TODO`, `FIXME`,
`XXX`, `???`, and `lorem ipsum` (case-insensitive) anywhere in the target's
prose are `failure`s, reported with line numbers. **Exemption:** text inside
fenced code blocks *and* inline code spans (single/double backtick) is masked
before the scan. The phase design exempts fenced blocks; this slice also
exempts inline code spans because specs and plans legitimately name these
tokens in backticks when describing tooling (this very document does), and an
inline-code mention is not an unfinished-work marker. Masking replaces exempt
regions with same-length spaces so reported line/column positions stay
accurate. Whole-token matching uses boundaries appropriate to each token
(word-boundary for the alphanumeric tokens; literal match for `???`).

**3. Referenced-path check.** Two syntaxes are scanned outside masked code
regions:

- **Markdown links** — `[text](path)`. A path that looks repo-relative but does
  not exist on disk is a `failure`.
- **Backtick-quoted strings** — an inline-code span whose content looks like a
  repo-relative path but does not exist is a `warning` (prose cites paths
  illustratively; a dangling backtick path is worth flagging but not blocking).

"Looks repo-relative" heuristic: the string contains `/` **and** either has a
file extension (a `.` in the final segment) or its first segment is a known
project directory (`docs`, `skills`, `tools`, `hooks`, `scripts`, `tests`,
`src`). Exemptions (skipped entirely, no finding):

- Anything inside a fenced code block (illustrative command/code).
- Paths containing placeholder/glob characters: `<`, `>`, `*`, `{`, `}`, `$`,
  `…` (e.g. `docs/specs/YYYY-MM-DD-<id>-slug.md`).
- Paths whose first segment is `docs/reviewer` (future/generated reviewer
  artifacts that legitimately do not exist yet).
- URLs (a scheme like `http://`, `https://`, `mailto:`).

Paths are resolved relative to `repo_root`. Absolute paths are resolved as-is.
Note the asymmetry: the markdown-link scan runs on text with **fenced blocks
masked but inline code visible** (so `[x](path)` links are seen); the backtick
scan reads inline-code spans directly. Fenced content is exempt for both.

**4. Kind-required sections.** Heading detection is keyword-based and tolerant
of phrasing — a heading line (`#`-prefixed) whose text matches the keyword
(case-insensitive substring) counts.

- `plan` → requires **both** a task section (a heading matching `task`, or the
  presence of any GitHub-style checkbox line `- [ ]` / `- [x]`) **and** a
  verification/acceptance section (heading matching `verif`, `accept`, or
  `gate`). A missing either is a `failure`.
- `spec` → requires an acceptance-criteria section (heading matching `accept`
  or `criteria`). Missing is a `failure`.
- `post-slice` / `post-phase` → require an evidence/verification section
  (heading matching `verif`, `evidence`, or `accept`) in the target. Missing is
  a `failure`.
- `design` / `implementation` / `other` → no required-section check (these
  kinds have no fixed shape).

**5. Context hygiene.** In the **standalone `preflight` subcommand**, a missing
`--file` target or a missing `--context` path is a `failure` surfaced in the
findings list (the subcommand has no other validation layer, so it must report
missing files itself). In the **`review` auto-preflight path** this case never
arises: `review` already hard-fails a missing target or context with **exit 2
before** chain discovery or the preflight gate (current
`external-reviewer.py` behaviour, preserved unchanged — so `--no-preflight`
stays byte-identical to today). Any existing context file larger than 16 KB
produces a `warning` naming the file and its size, hinting to pass
`tasktool brief <work-id>` output instead (this catches the
full-`docs/tasklist.json` habit S1.b discouraged in prose). The 16 KB warning
applies in both the subcommand and the auto-preflight path.

**Output and exit codes.** Text mode prints a grouped findings list
(failures first, then warnings) with a one-line summary; a clean run prints a
short "preflight passed" line. `--emit json` prints
`{"ok": <bool>, "failures": [...], "warnings": [...]}` where each entry is the
finding record. **Exit 0** = no failures (warnings allowed); **exit 4** =
one or more failures. Exit 4 is the phase-design-assigned preflight failure
code, deliberately distinct from the exit-3 resolution gate.

Exit 4 is also returned by `review` for a schema-too-new manifest. The two are
sequential, never simultaneous: in `review`, the manifest is read (and a
schema-too-new manifest aborts with exit 4) **before** the round number is
known, and the round-1 auto-preflight (S2.b) needs the round number, so it runs
strictly after the manifest read. A schema-too-new manifest therefore aborts
before preflight ever runs — preflight cannot mask it. The shared code is
accepted: both causes mean "input not reviewable, fix it," and introducing a
new code for preflight would diverge from the phase design's exit-4 assignment.

### S2.b — Auto-preflight on round 1

`review` runs `run_preflight_checks` in-process **before submitting a round-1
review** and refuses on failure, printing the same findings list and returning
exit 4. The gate fires only when `round_num == 1` (the broad first round).
Incremental rounds (N+1) skip it — the diff/resolution machinery already covers
them, and re-scanning an already-reviewed document for dangling paths adds
friction without catching revise drivers.

A new `--no-preflight` flag on the `review` subparser skips the auto-gate
entirely (escape hatch for an author who has deliberately accepted a finding, or
for non-standard documents). When skipped, behaviour is byte-identical to today.

The exact sequence inside `review` is: (1) resolve `--file` and `--context`
paths, **including the existing existence validation that returns exit 2 for a
missing target or context file** before any manifest or preflight work (this
check is preserved unchanged, so a missing file is never deferred into a
preflight exit-4 finding in the `review` path); (2) discover/read the chain
manifest — a schema-too-new manifest aborts here with exit 4; (3) apply the
resolution-required gate (round 2+ only);
(4) determine the round number from the chain; (5) **if `round_num == 1` and not
`--no-preflight`, run `run_preflight_checks` and return exit 4 on any failure**;
(6) only then construct the prompt and spawn the reviewer. The gate runs after
the round number is known but before any reviewer process is spawned, so a
failing preflight costs nothing in reviewer time. Warnings do not block — they
print to stderr and the review proceeds.

The chain folder is created (and the manifest eager-written) before the round
number is determined, so a round-1 preflight failure leaves an **empty chain
folder with no round artifacts**. This is acceptable: the empty folder is inert
and is reused on the re-run once the failures are fixed. No round entry, request
file, or response file is written for a preflight-refused round.

### S2.c — Self-review checklists

`brainstorming` (spec self-review section) and `writing-plans` (plan self-review
section) gain a short checklist of the top historical revise drivers, framed as
explicit author checks:

- Vague verification steps ("verify it works" with no command to run).
- Claims not grounded in the repo (referenced functions, flags, or files that
  do not exist).
- Tasklist drift (work-id, status, or dependency mismatch vs
  `docs/tasklist.json`).
- Acceptance criteria a reviewer cannot evaluate from the document alone.

Each checklist ends by instructing the author to run
`external-reviewer preflight --kind <kind> --file <doc>` (with the same
`--context` they will pass to `review`) and fix any failures before invoking
external review. `external-reviewer SKILL.md` documents the `preflight`
subcommand, the round-1 auto-gate, and `--no-preflight`.

## Acceptance criteria

1. `external-reviewer preflight --kind spec --file <doc>` exists, runs no LLM
   calls, and prints a findings list; `--emit json` prints
   `{"ok", "failures", "warnings"}`.
2. Each check class is caught on a purpose-built fixture **via the standalone
   `preflight` subcommand**: a placeholder token in prose (failure), a dangling
   markdown link (failure), a dangling backtick path (warning), a missing
   kind-required section (failure), a missing context file (failure, subcommand
   only), and an oversized (>16 KB) context file (warning).
3. A known-good document (no placeholders, all links resolve, required sections
   present, lean context) passes with exit 0 and zero failures.
4. Exemptions hold, with the placeholder scan and path scan treating inline
   code differently:
   - Placeholder tokens inside fenced code blocks **and** inline-code spans
     produce no placeholder finding.
   - A path inside a fenced code block produces no path finding.
   - A dangling repo-relative path inside an **inline-code span** produces a
     `warning` (it is scanned, not suppressed) — unless separately exempt.
   - Paths with glob/placeholder characters, `docs/reviewer/` paths, and URLs
     produce no path finding regardless of where they appear.
5. `external-reviewer review` auto-runs preflight on round 1 and returns exit 4
   (no reviewer process spawned) when a content failure is present;
   `--no-preflight` skips the gate and the review proceeds; round 2+ never runs
   the auto-gate. A missing `--file`/`--context` in the `review` path still
   returns exit 2 from the existing early validation (not deferred into
   preflight exit 4).
6. Exit codes: preflight content failures return 4, a clean preflight returns 0,
   warnings alone return 0; the `review` path's pre-existing missing-file
   validation continues to return exit 2.
7. `external-reviewer SKILL.md`, `brainstorming/SKILL.md`, and
   `writing-plans/SKILL.md` document the preflight subcommand, the round-1
   auto-gate / `--no-preflight`, and the self-review checklist with the
   revise-driver list.
8. The existing `skills/external-review/tests/` suite passes, and the new
   behaviours are covered by added tests, including at minimum: a unit test for
   `run_preflight_checks` distinguishing a dangling inline-code path (warning)
   from a fenced-code path (exempt); subprocess tests for
   `external-reviewer preflight --emit json` returning exit 0 (clean) and exit 4
   (failure present); a subprocess test proving round-1 `review` returns exit 4
   without spawning the reviewer on a failing target, and that `--no-preflight`
   reaches the reviewer command; a regression test pinning the
   manifest-read-before-preflight ordering (a schema-too-new manifest aborts
   with exit 4 before preflight runs); and a regression test that
   `review --context <missing>` on a would-be round-1 chain returns exit 2 from
   the existing validation (not exit 4 from preflight).

## Risks

- **Preflight false positives** (the path heuristic flagging illustrative
  prose). Mitigation: the exemption rules (fenced blocks, inline-code spans for
  placeholders, glob/placeholder characters, `docs/reviewer/` paths, URLs), the
  markdown-link-vs-backtick severity split (links fail, backticks warn), the
  `--no-preflight` escape, and validating the heuristic against the existing
  corpus of specs/plans in this repo before shipping.
- **Heading-keyword section detection too strict or too loose.** Mitigation:
  substring keyword match tolerant of phrasing, validated against this repo's
  existing specs/plans (which already use `## Acceptance criteria`,
  `## Verification`, `### Task N` headings and `- [ ]` checkboxes).
- **Version skew.** S2 adds a CLI subcommand and a flag; shims hard-fail on
  VERSION drift, so the change ships with a version bump and `install.sh` re-run
  per the release process (decided with the user at slice close).
