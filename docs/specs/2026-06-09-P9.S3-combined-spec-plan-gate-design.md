# P9.S3 — Combined spec+plan gate for small slices

**Date:** 2026-06-09
**Status:** draft
**Tracker:** P9.S3 (slice of P9 — Review-pipeline efficiency)
**Parent spec:** `docs/specs/2026-06-06-P9-review-pipeline-efficiency-design.md` (S3 section)
**Depends on:** P9.S1 (done), P9.S2 (done)

## Problem

Every slice in a Superstar-driven project pays for three review gates — spec,
plan, post-slice. The phase baseline (multistore, `external-reviewer stats`,
2026-06-06) shows spec chains averaging ~2.3 rounds and plan chains ~2.7. For a
small, single-surface slice — one tool or skill area, no new subsystem, no new
product decisions — the standalone spec review and the plan review largely
re-examine the same narrow change. The spec gate's rounds are avoidable in that
case: one review that covers both the plan and its (un-reviewed) spec would
catch the same defects at half the early-gate cost.

P9.S1 made each round cheaper (depth defaults, model tiering) and P9.S2 caught
mechanical defects locally before the first paid round (`preflight`). Neither
removed an entire gate. S3 closes that gap for eligible slices by folding the
spec review into the plan review.

## Goal

Let an eligible small slice skip the standalone spec review and instead carry
spec coverage into the plan review, halving the early-gate round count for those
slices without weakening review quality. Concretely:

- A `--combined-gate <spec-path>` flag on `external-reviewer review --kind plan`
  that attaches the un-reviewed spec to the plan review and instructs the
  reviewer to also review the spec, tagging spec-level findings distinctly.
- `chain.json` stamps `combined_gate` + the spec path per round so combined
  chains are identifiable after the fact.
- `external-reviewer stats` segments plan chains into combined vs standalone so
  the phase measurement plan can quantify the saving.
- `brainstorming` and `writing-plans` skill text defines eligibility and routes
  eligible slices through the combined gate.

This is S3 of the phase. It does not change the verdict contract, chain layout,
provider invocation, or any S1/S2 behaviour.

## Non-goals / out of scope

- No combined gate for phase-level specs — phase specs always receive a
  standalone spec review.
- No mechanical eligibility enforcement — eligibility is author judgment guided
  by skill text; the CLI does not gate on it.
- No changes to the verdict contract, chain-folder layout, merged-verdict truth
  table, or provider invocation shape.
- No changes to S1 behaviour (depth defaults, model tiering, resolution gate,
  base stats) or S2 behaviour (preflight) beyond the additive
  `combined_gate` stats segment.
- No consumer-repo (multistore) changes.

## Design

All CLI behaviour lives in
`skills/external-review/scripts/external-reviewer.py`. Skill text lives in
`skills/brainstorming/SKILL.md`, `skills/writing-plans/SKILL.md`, and
`skills/external-review/SKILL.md`. Tests live in
`skills/external-review/tests/`. Workflow-step verification touches
`tools/tasktool/` only with a regression test (no production code change
expected).

### S3.a — Eligibility (skill text)

`skills/brainstorming/SKILL.md` (spec flow) and
`skills/writing-plans/SKILL.md` (plan flow) gain a short "Combined spec+plan
gate" section. The combined gate applies to
**slice-level specs only** — a phase-level spec (like the P9 phase design)
always receives a standalone spec review.

A slice may use the combined gate when **all** of these hold:

- **Single-surface change** — one tool/skill/app area; no new subsystem.
- **No cross-repo or cross-plugin impact.**
- **Spec fits the existing phase direction** — no new product decisions that
  would otherwise warrant a standalone spec conversation.

When eligible, `brainstorming` still writes the spec document and commits the
spec artifact transaction, but **skips the standalone external spec review**;
it transitions directly to `writing-plans`. `writing-plans` then invokes the
plan review with `--combined-gate <spec-path>`, so the plan review carries the
spec-coverage burden. The author still sets `--workflow-step plan` after writing
the plan (see S3.c).

Ineligible or uncertain → today's two-gate flow (standalone spec review, then
plan review) unchanged. The skill text frames this as a judgment call with a
bias toward the standard two-gate flow: if any condition is doubtful, do not use
the combined gate.

### S3.b — `--combined-gate <spec-path>` flag

`external-reviewer review --kind plan --combined-gate <path/to/spec.md>` takes
the spec path as its explicit argument.

**Validation** (both surfaced before any chain or reviewer work, matching the
existing early-validation block at the top of the `review` dispatch):

- `--combined-gate` is valid **only with `--kind plan`** — any other kind exits
  **2** with a clear message.
- The spec path **must exist** — a missing path exits **2** with a clear
  message (same exit-2 idiom used today for a missing `--file`/`--context`).

**Context attachment.** The resolved spec path is added to the review's context
set so the spec is attached to the prompt and recorded as a context file. If the
same path was also passed via `--context`, it is **deduplicated** (attached
once) — resolved-path identity is the dedup key. This makes the spec attachment
verifiable from the flag rather than inferred from whatever `--context` happens
to carry (which also carries tracker files).

**Prompt guidance.** When `--combined-gate` is set, the plan `MODE_GUIDANCE` is
augmented with a spec-coverage instruction:

> This plan's spec did not receive a standalone review. Also review the attached
> spec for completeness, internal consistency, and groundedness; tag spec-level
> findings distinctly.

`make_prompt` currently formats `MODE_GUIDANCE[kind]` internally. To thread the
augmentation cleanly, `make_prompt` gains an optional `extra_guidance: str |
None = None` parameter; when set, it is appended to the kind's mode guidance
before formatting. The default (`None`) keeps every existing call byte-identical.
The guidance applies to **every round** of a combined chain (round-1 broad and
incremental follow-ups), since the spec remains un-reviewed throughout.

**Manifest stamp.** Each round entry (the dict assembled near
`external-reviewer.py:3312`) records:

- `combined_gate: true`
- `combined_gate_spec: <repo-relative spec path, resolved against repo root>`

Standalone plan rounds and all non-plan rounds do **not** carry these keys (see
Open decisions resolved below), so existing chains read back unchanged.

**Chain-level persistence and follow-up rounds.** A combined chain stays
combined for its whole life: the spec remains un-reviewed, so every round must
carry the guidance, attach the spec, and stamp the round. To make that robust
against the caller forgetting the flag on a re-submit, the **first round
persists `combined_gate_spec` at the chain (manifest top) level** — the same
place and precedent as the stored `work_id`. On any later round of that chain:

- If `--combined-gate` is **omitted**, the persisted chain-level
  `combined_gate_spec` is reused automatically — the spec is re-attached to
  context, the guidance is re-applied, and the round is re-stamped. The combined
  classification therefore cannot silently lapse on round 2+.
- If `--combined-gate <same-path>` is passed, behaviour is identical (idempotent).
- If `--combined-gate <different-path>` is passed, the run exits **6** with a
  chain-mismatch error — the same exit code and idiom used today for a
  `--work-id` that disagrees with the chain's stored value. (A combined chain
  cannot retroactively switch which spec it covers.)

A chain that was **not** combined on round 1 (no persisted `combined_gate_spec`)
and receives `--combined-gate` on a later round is rejected the same way (exit
6): the combined decision is made at chain start, not mid-stream. This keeps the
stats classification (any round combined ⇒ chain combined) consistent with the
per-round stamps.

### S3.b-stats — Combined-gate segmentation in `stats`

`collect_review_stats` classifies each **plan** chain in the window:

- **combined** if any in-window round has `combined_gate == true`;
- **standalone** otherwise.

A new top-level `combined_gate` block is added to the stats dict:

```
"combined_gate": {
  "combined":   {"chains": <int>, "rounds": <int>},
  "standalone": {"chains": <int>, "rounds": <int>}
}
```

`chains` counts distinct plan chains in each class; `rounds` counts in-window
round entries across those chains (round entries, matching the existing
per-kind `round_count` convention — not reviewer invocations). Only plan chains
are classified; non-plan kinds are not represented in this block.

`print_stats_table` prints one summary line after the per-slice line, e.g.:

```
combined-gate (plan): combined=<chains>c/<rounds>r  standalone=<chains>c/<rounds>r
```

`--json` output carries the same `combined_gate` block. When there are no plan
chains in the window, both classes report zeros (the block is always present
for a stable schema).

### S3.c — Workflow-step compatibility (verify-only)

The combined-gate flow sets `tasktool set <slice-id> --workflow-step plan`
directly from spec-written state, without an intervening spec-review-passed
step. This must not be blocked.

**Verified during this slice's design:** `tools/tasktool` enforces no
step-ordering precondition — `_validate_set_flags`
(`tools/tasktool/commands.py:110-117`) only checks that the supplied step value
is a member of the allowed set for the row kind (slice:
`{spec, plan, implement, done}`). There is no rule requiring the spec step or a
passed spec review before `plan`. So `set --workflow-step plan` from spec state
already works.

S3 therefore makes **no tasktool production change**. It adds a regression test
asserting `tasktool set <slice> --workflow-step plan` succeeds when the row's
current step is `spec` (pinning the no-precondition behaviour against future
drift) and documents the combined-gate step transition in the skill text.

## Acceptance criteria

1. `external-reviewer review --kind plan --combined-gate <spec>` injects the
   spec-coverage guidance into the plan prompt (assertable: the guidance text
   appears in the round-1 request prompt), attaches the spec to the context set
   (deduplicated if also in `--context`), stamps `combined_gate: true` plus the
   spec path in the `chain.json` round entry, and persists `combined_gate_spec`
   at the chain (manifest top) level.
2. On a later round of a combined chain: omitting `--combined-gate` reuses the
   persisted `combined_gate_spec` (the round prompt still carries the guidance,
   the spec is re-attached, and the round is re-stamped `combined_gate: true`);
   passing `--combined-gate <different-path>` exits **6** (chain mismatch); and
   passing `--combined-gate` on a chain that was not combined on round 1 also
   exits **6**.
3. `--combined-gate` with any kind other than `plan` exits **2**, and
   `--combined-gate <missing-path>` exits **2** — both without spawning a
   reviewer or creating a chain folder.
4. A standalone plan review (no `--combined-gate`) is byte-identical to today:
   no `combined_gate` guidance in the prompt, and `make_prompt`'s default
   `extra_guidance=None` leaves the assembled prompt unchanged.
5. `external-reviewer stats` (text and `--json`) reports a `combined_gate`
   segment classifying plan chains into combined vs standalone with per-class
   chain and round counts; a fixture with one combined plan chain and one
   standalone plan chain yields `combined: {chains: 1, ...}` and
   `standalone: {chains: 1, ...}`; a window with no plan chains yields zeros in
   both classes.
6. `tasktool set <slice-id> --workflow-step plan` succeeds when the row's
   current `workflow_step` is `spec` (regression test pinning the
   no-precondition behaviour); no tasktool production code changed.
7. `skills/brainstorming/SKILL.md`, `skills/writing-plans/SKILL.md`, and
   `skills/external-review/SKILL.md` document the combined-gate eligibility
   rules (slice-only, three conditions), the brainstorming "write spec but skip
   standalone review" branch, the `--combined-gate` invocation in writing-plans,
   and the `--workflow-step plan`-from-spec transition.
8. The existing test suites pass, and the new behaviours are covered by added
   tests: AC 1–5 by unit/subprocess tests in `skills/external-review/tests/`
   (including a round-2 fixture proving combined-gate persistence — guidance,
   spec re-attachment, and `combined_gate` stamping on round 2 without the flag,
   plus the exit-6 mismatch); AC 6 by a regression test in
   `tools/tasktool/tests/` for the `spec → plan` workflow-step transition.
   Run `pytest skills/external-review/tests tools/tasktool/tests`.

## Open decisions resolved

- **`combined_gate` absent vs `false` on standalone rounds.** Standalone and
  non-plan rounds omit the `combined_gate`/`combined_gate_spec` keys entirely
  (rather than writing `combined_gate: false`). Stats classification treats a
  missing key as not-combined, so absence is unambiguous and keeps existing
  chains byte-stable on read-back. (Either is acceptable for AC1; the spec picks
  omission for minimal manifest churn.)
- **Stats `rounds` unit.** The `combined_gate` segment counts round entries
  (consistent with the per-kind `round_count`), not reviewer invocations. The
  reviewer-invocation count is a per-slice-metric concern (S1.e) and is not
  duplicated here.
- **Guidance scope across rounds.** The combined-gate guidance is applied on
  every round of a combined chain, because the spec stays un-reviewed for the
  life of the chain. Persistence is achieved by storing `combined_gate_spec` at
  the chain (manifest top) level on round 1 and auto-reusing it on later rounds
  (the `work_id` precedent), so a re-submit that omits the flag does not silently
  drop spec coverage; a later explicit different spec path is a chain mismatch
  (exit 6). See S3.b "Chain-level persistence and follow-up rounds."

## Risks

- **Quality regression from dropping the standalone spec gate.** Mitigation:
  the combined gate is opt-in and narrowly scoped (single-surface, no new
  product decisions); the plan reviewer is explicitly instructed to review the
  attached spec and tag spec findings distinctly; the post-slice gate
  (unchanged, `thorough`, strong model) remains the safety net; and the phase
  measurement plan watches post-slice revise rate as the canary, segmenting
  combined chains via the new `combined_gate` stamp.
- **Author misjudges eligibility** (uses the combined gate for a slice that
  warranted a standalone spec conversation). Mitigation: skill text biases
  toward the two-gate flow on any doubt; the conditions are conjunctive (all
  must hold); ineligible-but-used cases still get full plan + spec coverage in
  one review, so the failure mode is "slightly less spec scrutiny," not "no
  spec scrutiny."
- **Version skew.** S3 adds a CLI flag and a stats field; shims hard-fail on
  VERSION drift, so the change ships with a version bump and `install.sh` re-run
  per the release process (decided with the user at slice close).
